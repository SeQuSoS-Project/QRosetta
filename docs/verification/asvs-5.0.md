Nothing is stored as a file under a name the client chooses; ZIP members of crates and bundles are written by the server under fixed or slugged names (`test_export_trust.py`).

## Sign-in protection

Sign-in is limited to 10 attempts a minute per client address and registration to 5, checked before bcrypt; failed attempts count. There is no per-account lockout, so guesses at one account from many addresses are limited only by bcrypt's cost and by those per-address limits. Every failed sign-in is logged (`auth.login_failed`, with the email's SHA-256 prefix), so a pattern across addresses is visible in the security log. Passwords need 8 characters to 72 bytes and may not be one of 2,086 common passwords.

## Sessions

A session is a bearer token (HS256 JWT, `aud=qrosetta-api`) that expires 30 minutes after sign-in; there is no refresh token and no inactivity timeout shorter than that. A user may hold any number of sessions; sign-out or a password change ends all of them (`tokens_valid_after`). Operators end one user's sessions by deactivating the account (`users.is_active = false`) and everyone's by changing `SECRET_KEY`. This follows NIST SP 800-63B AAL1 (single factor, reauthentication at least every 30 days; here every 30 minutes).

## What a job id gives

A job id (UUID4) is a capability: whoever holds it can read the job's status, report, summary, circuits and export while the job is kept (30 minutes by default, 24 hours in the local compose file). Only the account that submitted a signed-in job may save it to history. Saved runs, saved circuits and share links are readable only by their owner (share links: the allowlisted circuit texts, to whoever holds the link token).

## Transport

Local mode publishes nginx on 127.0.0.1:8080 over plain HTTP. Publishing it on another address (`qrosetta start --bind`) needs a TLS terminator in front that sends HSTS; the API trusts X-Forwarded-For only from the proxies in `QROSETTA_TRUSTED_PROXIES`. Under rootless podman, nginx sees one address for every client (the engine's network gateway), so an exposed stack would key every client's rate limits together; put the TLS terminator on the host and pass the client address with `QROSETTA_PROXY_TOKEN`. The Cloud Run frontend and the Rahti route serve TLS 1.2 and 1.3 only, with HSTS.

## Outbound connections

From the browser: the server's own origin; `https://quirk-e.dev` (the Quirk view, a frame); `https://cdn.jsdelivr.net` (ReDoc on `/redoc` only, with an SRI hash). From the server, local mode: none (runners and compilers sit on an internal network without internet). Kubernetes mode: the Kubernetes API, the S3 store (CSC Allas) and the PostgreSQL database (CSC Pukki); the Cloud Run frontend proxies to the Rahti route. Build and release time: package indexes, snapshot.debian.org, GHCR and Sigstore.

## Logs

The API writes three streams to stdout, kept by the container engine (`qrosetta logs`, `podman logs`): the application log (`time | level | service | message`), the access log (uvicorn), and the security log (`rosetta-security-events`, one JSON object per line: sign-ins, failed sign-ins, registrations, sign-outs, password changes, account deletions, 401/403 answers, cross-site refusals, rate-limit hits). nginx writes its access and error logs to its container's stdout and stderr. No password, token or request body is logged; emails appear in the security log only as a SHA-256 prefix. Retention is the engine's; a public deployment should ship the security log to a separate store.
