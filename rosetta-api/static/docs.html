Documentation

QRosetta

QRosetta takes one quantum circuit and runs it on many different quantum simulators. It then compares the results and shows where the simulators agree and where they differ.

Overview

You provide one circuit, written in OpenQASM 2.0. QRosetta sends that circuit to a set of simulator backends, currently including Qiskit (via Aer), Cirq, qsim, qibo, PennyLane, Qulacs, QuEST, quimb, myQLM, PyQuil, Qrisp, cuQuantum, and TorchQuantum. Several of these are accessed through pytket. Every backend receives the circuit in the same request format and returns its result in the same response format, so the results can be compared directly.

QRosetta then compares the backends pairwise. For each pair, it checks whether their outputs agree and, if they don't, whether a known cause explains the difference. See Agreement classification for how that works.

QRosetta compares outputs against each other; it has no independent way to check whether any of them is mathematically correct. If two backends disagree and you need to determine which one (if either) is right, that requires a different kind of analysis than QRosetta performs.

Quickstart

  1. Enter an OpenQASM 2.0 circuit, or generate a preset (GHZ, Bell, QFT, Grover, Bernstein–Vazirani, VQE, random) or pull one from a benchmark suite.
  2. Every backend the server has enabled runs by default; the line above the run button says how many are selected. Open the Config drawer to deselect backends (the choice is remembered in this browser) or to set the timeout, optimization level, sampling seed and agreement thresholds.
  3. Pick a run mode, statevector or measured, and run.
  4. Read the report tabs: Summary, Performance, Resources, Divergence, Agreement, Artifacts, and Exports.

Inputs are checked before a run is submitted: a shot count, timeout, seed or threshold that is out of range is marked next to the field and the run is not sent. Requests the server rejects (an empty circuit, an unknown or disabled backend, an optimization level outside 0–3, a timeout below the minimum) are shown with the server's message. If the page is reloaded while a run is in progress, the page offers to show that run's results when it loads again, and the editor keeps the last circuit.

Tip. The Batch panel lets you queue several circuits and run them together in one job; you can export/import the queue as a JSON "playlist" file for repeatable suites.

Circuit sources

A circuit can come from any of four places:

  • Manual entry. Paste or type OpenQASM 2.0 directly into the editor.
  • Presets. The circuit generator builds a preset family (GHZ, Bell, QFT, Bernstein–Vazirani, Grover, and others) at a qubit count you choose.
  • QASMBench. A bundled suite of fixed-size circuits, selected by name.
  • MQT Bench (Munich Quantum Toolkit). A bundled suite of algorithm-level circuits, selected by algorithm and qubit count.

The Benchmarks drawer covers the last two: pick a suite, then either load one circuit into the editor, add it to the batch queue, or use the bulk-select list (with a name filter and a qubit-count cap) to add many circuits to the batch queue at once.

Run modes

ModeWhat each backend returnsHow QRosetta compares
Statevector The full output state amplitudes (no sampling). Fidelity and global phase offset arg⟨a|b⟩ between normalised state pairs. No seed is used.
Measured A histogram of measurement outcomes over a chosen number of shots. Jensen–Shannon divergence (in nats) and Hellinger distance between the count distributions, each normalised by its observed total, plus a shot-noise statistical test.

In statevector mode the API removes measurements at the end of the circuit before dispatch and lists that as an API: entry in preprocessing_applied. A circuit with a measurement followed by further operations, a reset, or an if is rejected with HTTP 400 in statevector mode, because it has no single output statevector; run it in measured mode. In measured mode these operations are passed to every backend; adapters that cannot simulate mid-circuit measurement, reset or classical control return an error for that backend.

Statevector runs are limited to 18 qubits and measured runs to 24 (the server reports its limits at GET /config), because a full statevector grows as 2n. Each backend's run ends with one of four dispatch statuses: ok, error (the backend rejected the circuit or crashed), timeout (the run exceeded the timeout) or offline (the runner could not be reached). A failed run's timing and memory fields are null, not 0. Any pair involving a failed run is reported as not comparable.

Each result can also report device (CPU or GPU), simulator_backend (the library that executed the circuit) and simulation_method. The Summary tab's per-backend details and the Performance and Resources tables show them as tags. Qiskit runs on qiskit-aer's AerSimulator with method="statevector". The cuQuantum runner is qiskit-aer-gpu 0.15.1 with cuStateVec enabled, running on an NVIDIA GPU; its results also carry gpu_name and custatevec_enabled. On a server without an NVIDIA GPU it is listed as unavailable in the Config drawer, with the reason the server gives, and it is not dispatched; it never falls back to the CPU. Its kernels run on the GPU, while its host-side work (parsing, launching kernels, copying results back, sampling) runs under the same 0.5-CPU quota as the other runners (see Resources, queueing and timeouts). A time comparison between cuQuantum and a CPU backend therefore compares different hardware.

Each backend reports the amplitude precision it simulated in. Most use complex128; qsim, Qrisp, TorchQuantum and Cirq's measured path use complex64, and cuQuantum reports the precision its simulator was configured with. The report tabs show a precision badge per backend; a complex64 backend's fidelity against a complex128 one carries single-precision rounding error.

Circuit preprocessing

Changes to the circuit happen in two places, and both are recorded in each backend's preprocessing_applied list.

  • API-side (entries starting API:, tagged API in the UI). The API prepares one circuit per dispatch group. With Apply SDK Preprocessing on:
    • Statevector mode: terminal measurements are removed, several quantum registers are merged into one in declaration order, and the circuit is parsed and re-emitted with pytket with barriers removed.
    • Measured mode, both groups (measured_native, backends that sample with their own sampler, and measured_sampled, backends that sample a statevector): register merge, then the pytket round-trip with barriers removed.
    The pytket round-trip inlines custom gate definitions, rewrites gates into pytket's QASM gate set (for example u becomes u3, with angles as multiples of π) and expands register broadcasts. In measured mode the native group also receives a measure-all when the circuit has no measurements; this happens with preprocessing off too. With preprocessing off there is no register merge and no pytket round-trip in any group; statevector mode still removes terminal measurements. The report's dispatched_circuits lists which runners were in which group.
  • Runner-side. Each backend's own passes (gate rebasing, barrier stripping, the backend's default compilation pass at every optimization level). Passes the adapter needs regardless of the setting say so in their text.

The RO-Crate stores the original circuit (circuit.qasm), each circuit the API dispatched (dispatched_circuits/, one per runner group) and the circuit each backend executed (transpiled_circuits/).

Batch runs and experiments

The Batch panel queues several circuits and runs them together as a single job, in either statevector or measured mode. Circuits can be added manually, from the generator, or from the Benchmarks drawer, including a whole suite at once capped by qubit count. A progress indicator shows which queued circuits are done, running, or still queued. The queue can be exported to a JSON file and re-imported later. A batch shares one master seed.

Freezing a batch as a reproducible experiment

Checking "Freeze as reproducible experiment" inside the Batch panel runs the same queued circuits over one or more preprocessing axes (each backend's preprocessing on, off, or both) and packages the result into one ZIP bundle containing:

  • The input QASM for every circuit, frozen at run time.
  • A conformance matrix recording whether each circuit ran on each backend. Every error carries an untriaged marker for you to classify as an adapter issue, an SDK issue, by-design behaviour, or a resource limit. The software does not classify errors itself.
  • An agreement-prevalence table: how many backend pairs received each agreement label.
  • A manifest recording the git commit, executed SDK versions and the seeds used.

Agreement classification

Two simulators can produce different-looking outputs because of a different qubit-ordering convention (endianness) or an unobservable global phase. For each backend pair, QRosetta checks a fixed list of transforms in order and reports the first one under which the two outputs agree, with the metric before and after it.

A statevector pair agrees when its fidelity, computed on normalised vectors and stored unrounded, is at least 1 − fidelity_tolerance. The default tolerances are fidelity_tolerance = 1e-5, phase_tolerance = 1e-6 rad, norm_tolerance = 1e-4, js_threshold = 0.01 nats and hellinger_threshold = 0.1 (the server reports its defaults at GET /config). They can be changed in the Config drawer; the values sent are recorded in the report's run configuration and in every pair record, and the pair record's values are the ones the label was computed with. The phase tolerance of 1e-6 rad sits above single-precision rounding (about 1e-7 for complex64), so a complex64 backend is not reported as carrying a global phase because of rounding alone.

The measured labels are descriptive distance checks, and at small shot counts two samples of the same distribution routinely exceed them. Whether a measured pair disagrees is decided by its measured_assessment, derived from the shot-noise test:

measured_assessmentMeaning
consistent_within_shot_noiseNeither test is significant after BH correction, and the power to detect a total-variation gap of 0.05, computed at α/m, is at least 0.8. This holds even when the label is distance_exceeds_threshold. It is a failure to find a difference at that power, not a demonstration that the distributions are equal.
inconclusive_low_shotsEither some expected counts are below 5 after rare outcomes are pooled (inconclusive_reason: low_expected_counts), or neither test is significant but the power to detect the target gap, computed at α/m, is below 0.8 (low_power). resolvable_by_more_shots records whether more shots can resolve the pair; it is false when the outcomes are too rare for the test at any practical shot count. The pair is neither consistent nor in disagreement; the Summary tab groups these pairs by cause and gives the shot count the power model recommends when it exceeds the shots used.
distinguishableBoth tests are significant after BH correction. This is the only measured outcome the Summary tab counts as a disagreement.
ambiguousExactly one of the two tests is significant. Treated as inconclusive, not as a disagreement.
not_comparableThe pair has no usable counts on at least one side.

Reports that predate measured_assessment are read from metrics.statistical_test.verdict instead (consistent, inconclusive_low_shots, distinguishable, ambiguous). A measured pair whose observed shot totals differ from the requested n_shots records both in metrics.shot_total_mismatch.

Transforms are an analysis step on top of the stored data. When a pair is labelled "after bit reversal", the report shows both the direct metric and the post-transform metric. Each backend's output is stored as that backend returned it.

Metric formulas

Statevectors

Each backend's statevector a is normalised first: â = a / ‖a‖₂. The norm ‖a‖₂ is recorded in metrics.norms; if |‖a‖₂ − 1| > norm_tolerance for either side, the pair is flagged unnormalized_input.

  • Direct fidelity: F = |⟨â|b̂⟩|² = |Σₖ conj(âₖ) b̂ₖ|², clamped to [0, 1] and stored unrounded.
  • Global phase offset: φ = arg⟨â|b̂⟩ in radians, in (−π, π]. A value with |φ| ≤ phase_tolerance is reported as 0. This is the overall phase between the two states; a relative phase between components of a superposition shows up as reduced fidelity instead. The JSON field keeps its name, direct_relative_phase_rad, and the matrix is relative_phase_matrix.
  • Bit-reversed fidelity: F_rev = |⟨â|R b̂⟩|², where (R b)ₖ = b_rev(k) and rev(k) reverses the n-bit binary representation of the index k.
  • Permutation fidelity: the largest |⟨â|P_π b̂⟩|² over every permutation π of the n bit positions other than the identity and the reversal; P_π reshapes the vector to n axes of size 2 and transposes them by π. Ties keep the lexicographically first permutation. The search runs for n ≤ 7 qubits; above that the pair records too_many_qubits.

Labels are assigned in this order, with ε = fidelity_tolerance: agree_directly if F ≥ 1 − ε and |φ| ≤ phase_tolerance; agree_up_to_global_phase if F ≥ 1 − ε; agree_after_bit_reversal if F_rev ≥ 1 − ε; agree_after_qubit_permutation if the permutation fidelity is ≥ 1 − ε; otherwise residual_disagreement. An agreeing pair with unnormalized_input is relabelled agree_after_normalization. The Summary tab quotes the fidelity under the transform the label names, with the direct fidelity beside it.

Counts

Each backend's counts c(x) are normalised by its own observed total: p(x) = c(x) / Σₓ c(x), over the union of outcomes of the two backends.

  • Jensen–Shannon divergence: JS(p, q) = ½ Σ p ln(p/m) + ½ Σ q ln(q/m) with m = (p + q)/2, natural logarithm, so it is in nats and lies in [0, ln 2 ≈ 0.693].
  • Hellinger distance: H(p, q) = (1/√2) ‖√p − √q‖₂ = √(1 − Σ √(p q)), in [0, 1].
  • Total variation distance: TV(p, q) = ½ Σ |p − q|, in [0, 1]; recorded as statistical_test.effect_size.total_variation.

A measured pair is distance_within_threshold when JS ≤ js_threshold and H ≤ hellinger_threshold; the bit-reversed and permuted counts are tried next, as for statevectors.

Shot-noise tests

The two backends' counts form a 2 × K contingency table O over the K outcomes observed by either backend (outcomes with zero counts on both sides are dropped). The table is built in the label-aligned basis: when the two backends declare different bit orders (lsb against msb), the second backend's keys are bit-reversed first; otherwise the keys are compared directly. The basis comes from the declared orderings, not from which basis gives the smaller distance, and is recorded as statistical_test.basis. Outcomes whose expected count is below 5 are pooled into one bin, and more of the rarest outcomes are merged in until the pooled bin reaches an expected count of 5 or the table meets Cochran's rule (no expected count below 1, at most 20% below 5); pooled_outcomes records how many outcomes were merged. With row totals Rᵢ, column totals Cⱼ and N = Σ O, the expected counts are Eᵢⱼ = Rᵢ Cⱼ / N.

  • Pearson chi-square: χ² = Σ (O − E)² / E, no continuity correction, df = K − 1.
  • G-test: G = 2 Σ O ln(O / E), same df.
  • Cramér's V: √(χ² / N).
  • Multiple comparisons, over the m tested pairs of the run, separately for each test. Benjamini–Hochberg: with p-values sorted p₍₁₎ ≤ … ≤ p₍ₘ₎, p̃₍ₖ₎ = min over j ≥ k of min(1, m p₍ⱼ₎ / j). Bonferroni: min(1, m p). A test is significant when its BH-adjusted p-value is below α = 0.05. BH controls the false discovery rate at q = α: among the pairs it flags, up to a fraction q are expected to be flagged by chance, so one or two flagged pairs in a run with many can be false discoveries. This guarantee assumes the tests are independent or positively dependent (PRDS). Pairs that share a backend share that backend's sample, so their tests are dependent, and PRDS has not been established for chi-square statistics that share a sample. A p-value that underflows to 0 is shown as <1e-300, and values below 1e-3 in scientific notation.
  • Verdict: inconclusive_low_shots (low_expected_counts) if no pooling gives adequate expected counts; else distinguishable if both tests are significant, ambiguous if exactly one is, and, if neither is, consistent when the power at the observed shots, computed at α/m, is at least 0.8 and inconclusive_low_shots (low_power) otherwise. resolvable_by_more_shots, beside inconclusive_reason, says whether more shots can turn an inconclusive pair into a verdict.
  • Power model: the effect size is Cohen's w = δ with δ = 0.05, the smallest w any distribution pair at total variation δ can have (w ≥ TV). The chi-square statistic then follows a noncentral χ² with df = K − 1 and noncentrality λ = N w². power_to_detect_delta_at_observed_shots = 1 − F(χ²₁₋α′,df ; df, λ) with α′ = α/m, the Bonferroni level for the m tested pairs of the run (recorded as power.alpha_used and power.m_pairs). α/m is at most the level BH applies to any pair, so the power figure does not overstate the chance that the corrected test flags a gap of size δ. It is still the power of the chi-square test alone; the verdict needs both tests to be significant. and recommended_shots_per_backend (also recorded under its earlier name shots_per_backend_for_target_power) is ⌈N*/2⌉, where N* is the total giving power 0.8 at α/m. recommended_exceeds_actual says whether that is more than the shots either backend used; the Summary tab recommends more shots only then. Because df uses the observed outcomes, the recommendation can be too small when the true support is larger.

Bit order per backend

Each result declares qubit_ordering: msb when qubit 0 is the most significant bit of the statevector index or counts bitstring, lsb when it is the least significant. The Summary tab reports whether a bit-reversed pair's declared orderings actually differ; bit reversal between two backends declaring the same ordering points to a wrong label or a defect.

Counts keys

A counts key is a bitstring over every classical bit the circuit declares, including bits no measure statement writes; those read 0. Classical bits get one flat index in creg declaration order: with creg c[2]; creg d[3];, c[0], c[1] are bits 0 and 1 and d[0]…d[2] are bits 2–4. In an lsb key, classical bit 0 is the rightmost character; in an msb key it is the leftmost. A circuit without measurements, in measured mode, gets a measure-all appended for backends that sample natively (see Circuit preprocessing).

The shot-noise statistical test

In measured mode a fixed distance threshold is descriptive. With few shots, two samples of the same distribution can still differ noticeably. Alongside the JS/Hellinger label, QRosetta reports for every comparable pair:

  • A Pearson chi-square test (no continuity correction) and a G-test of homogeneity between the two count vectors, in the basis the two backends' declared bit orders select, with rare outcomes pooled;
  • Benjamini–Hochberg (FDR) and Bonferroni adjusted p-values across all pairs of the run;
  • Effect size (total variation, Cramér’s V) and a power estimate at α/m that uses the observed degrees of freedom (power.df).

The verdict is consistent, distinguishable, inconclusive_low_shots or ambiguous, from the BH-adjusted p-values at α = 0.05; Metric formulas gives the statistics, the corrections and the power model. Each backend samples with its own derived seed, so two backends never draw the same shot sequence; shared_seed records whether a pair's runner seeds were equal.

Reproducibility

  • Seeds. Every measured run has a master seed: the one you set in the Config drawer, or one the API generates and records at seed. Each backend receives runner_seed = the first 4 bytes of sha256("<master seed>:<runner key>"), read big-endian, top bit cleared; the runner key includes any ~opt<L>~run<N> suffix. The formula is recorded at seed_derivation. seed_honoured is false for a backend whose sampler ignores the seed (Braket, currently disabled).
  • Executed SDK versions are captured by each backend and written into the provenance.
  • Run configuration. Reports record the agreement thresholds sent, the timeout and its scope, the optimization levels, apply_preprocessing, the API-side preprocessing, the dispatched circuits, started_at / finished_at and the git commit (git_sha). The divergence report records analysis_version, the version of the classification and test rules. Runner image digests are recorded only when the deployment sets QROSETTA_IMAGE_DIGESTS; in local mode the report says "not recorded". Each result carries runner_code_sha256, the sha256 of the runner's code, which identifies the adapter that produced it.
  • Statevector hashes. A report stored without statevectors keeps statevector_sha256 and the length. The hash is not stable across replays for every backend: Cirq, for example, can differ in the last bits of some amplitudes between two runs of the same circuit. Compare replayed statevectors by fidelity.
  • RO-Crate export. A run exports as an RO-Crate conforming to the Process Run Crate profile, with the inputs, dispatched and executed circuits, per-backend results, agreement evidence and provenance.

Replaying a run

  1. Take the circuit from the crate's circuit.qasm (circuits/ for a batch) or the experiment bundle's inputs/*.qasm, which hold the text as submitted; for a bundle, check each file against the manifest's qasm_sha256. Submit it as literal QASM; do not regenerate a preset.
  2. Send the effective values rather than the requested ones: the seed from results.seed (for an experiment, effective_seeds_per_axis); the thresholds from the report's agreement_thresholds, sent explicitly, because defaults can change between versions; an explicit runner list taken from raw_results[].simulator, because an empty list means every runner enabled at the time; and n_shots, apply_preprocessing, optimization_level, runner_config, runner_phases and timeout_seconds.
  3. Compare in this order: runner_seed per backend; the dispatched and transpiled circuits; counts, byte for byte; statevectors by fidelity; then the verdicts.
  4. If git_sha, analysis_version or a backend's runner_code_sha256 differs between the two reports, verdicts can differ even when the counts are identical, and a changed adapter can change that backend's output. Re-derive the verdicts on the new version rather than comparing labels.

Timing and memory methodology

  • One warm-up, one timed run. Each backend runs the circuit once and discards the result, then runs it once more for the reported numbers. Every timing is a single sample (timing_samples = 1), so run-to-run variation is not measured.
  • Timing windows. compilation_time_sec is wall clock from t0 to t1 (parse, transpile, build the native circuit); simulation_time_sec is wall clock from t2 to t3 (execute, return the statevector or draw the shots). Building a counts histogram from drawn shots is outside the window.
  • cuQuantum's timed window. cuQuantum's simulation_time_sec covers sim.run(qc).result(): Aer's conversion of the circuit, GPU memory allocation, the cuStateVec kernels and the copy of the result from device to host. CUDA context initialisation happens in the warm-up run, outside the window; it shows up in cpu_time_sec, which covers the whole process.
  • CPU time. simulation_cpu_time_sec is process CPU time (all threads) over t2..t3 only. cpu_time_sec covers the whole isolated runner process: interpreter start, SDK import, warm-up and the timed run.
  • Threads. Every runner is started with OMP_NUM_THREADS, MKL_NUM_THREADS, OPENBLAS_NUM_THREADS and NUMEXPR_NUM_THREADS set to 1; the values each run saw are in thread_env.
  • Memory. Memory is read from the kernel high-water mark (VmHWM). memory_usage_mb (Sim-window RSS delta) is the peak RSS minus the baseline RSS over the simulation window (pre-execute setup plus t2..t3; the high-water mark is reset when the window opens). process_peak_mb (Sim-window peak RSS) is the absolute peak over the same window. process_peak_rss_mb is the peak RSS of the simulating process over its whole life; Resources are ranked by it. memory_method and process_peak_rss_method record the method; where VmHWM is unavailable they read sampled_10ms (RSS polled every 10 ms, which can miss short peaks) and getrusage (ru_maxrss), and the UI shows a badge.
  • Host memory only. Every memory field is host RSS. GPU device memory is not measured, so a GPU run's memory fields do not include its statevector on the GPU. GPU runs are not ranked by memory; they are listed under unranked with reason gpu_memory_not_measured, and the Resources tab says so.
  • Units. Every memory field ending in _mb is in MiB (220 bytes).
  • What dominates memory. For small circuits, process_peak_rss_mb is dominated by the Python interpreter and the SDK's import footprint, and is far larger than the statevector; compare it with theoretical_statevector_mb. Differences between backends at small n reflect their libraries, not their simulation algorithms.
  • Gate count and depth come from the circuit each backend executed (its transpiled_qasm), using greedy layering for depth.
  • Rankings include only successful runs. Failed runs, and GPU runs in the memory ranking, are listed under unranked with a reason, and the UI shows them after the ranked rows. The Performance and Resources tables have a Device column, and the batch summary tags the device of each Fastest and Lightest backend.

Resources, queueing and timeouts

  • CPU quota. Each runner is limited to 0.5 CPU (local mode: a Docker CPU limit of 0.5 and 512 MiB of memory; Kubernetes mode: a 0.5 CPU limit and 1 GiB), and its math libraries run one thread. A process that needs a full core is throttled under this quota, so wall-clock simulation_time_sec can exceed simulation_cpu_time_sec. The cuQuantum runner's container has the same quota: its kernels run on the GPU, but its host-side work (circuit conversion, kernel launches, synchronisation, the device-to-host copy and sampling) is throttled like any other runner's.
  • One run at a time per runner. A runner executes one run at a time. When several jobs, yours or other users', target the same runner, later runs wait for it. The wait is recorded as queue_wait_sec and is not part of any timing. Waits of 0.5 s or more are shown in the per-backend details and as a "queued" tag in the Performance and Resources tables; shorter values are dispatch overhead. In local mode a run may wait at most the server-wide cap RUNNER_QUEUE_MAX_WAIT_SEC (default 1800 s, recorded in the report as queue_max_wait_sec); a run still queued at the cap is not started and is reported with never_started: true.
  • Timeout scope. The timeout set in the Config drawer (the server's allowed range is shown under the field) applies to each backend separately and covers starting the isolated runner process, importing the SDK, the warm-up run and the timed run. In local mode the budget starts when the run leaves the runner's queue, so time spent waiting for a busy runner does not count against it; the queue wait has its own cap, independent of the timeout (see the previous item). In Kubernetes mode it runs from Job creation and also covers pod scheduling, image pull and the result upload. The report records the scope that applied. A backend that exceeds it ends with status timeout. The value in the field is sent with every run from the page; API calls that omit timeout_seconds use the schema default shown in the Swagger UI.
  • Single sample. Every timing is one timed run after one warm-up, so a difference between two backends smaller than the run-to-run variation of either cannot be read from one report. Repeat the run (or use multi-run mode) to see that variation.

The distinguishable group carries a note on expected false discoveries under the BH correction. The success banner appears only when at least two backends succeeded and every pair agrees without a transform (in measured mode: every pair is consistent within shot noise and within the thresholds in the label-aligned basis); it states the tolerance or α that was tested. A collapsible section lists the analysis version and git commit, then per-backend device (with the GPU name and cuStateVec state for a GPU run), simulator backend, precision, seeds, queue wait, memory method, runner code hash, thread settings and preprocessing.
Performance / ResourcesRanked successful runs, then the unranked runs with their status and reason, with a Device column (GPU runs name the GPU). Tooltips on each column give the measurement window. When a GPU run is present, the Performance note says that times across devices compare different hardware and the Resources note says that GPU device memory is not measured.
DivergenceThe N×N fidelity, global phase offset arg⟨a|b⟩, JS-divergence (nats) and Hellinger matrices. A cell is green when it is within the tolerance recorded with that pair; OFF, ERR and T/O mark failed runs, n/c a pair that is not comparable (null in the report; reports from older versions use −1). The diagonal holds each backend compared with itself (fidelity 1, JS 0, phase 0). Values are unrounded: a fidelity other than 1 is printed with enough decimals to differ from 1, and non-zero values below 1e-3 in scientific notation.
AgreementThe label per backend pair, with the metrics, the tolerances used, the statistical test and provenance (seeds, ordering, SDK versions, preprocessing) per pair.
ArtifactsPublication figures and tables (SVG/PNG/PDF; LaTeX/CSV/HTML/Markdown/XLSX), scoped to any subset of backends in the browser.
ExportsThe JSON report held in the browser, the full report from the server, and the RO-Crate export (see Reports and exports).

A batch or experiment run shows a suite summary and the Exports tab. The suite summary gives each circuit an agreement badge (All pairs agree, Explained / partial, Inconclusive, Anomaly, Not compared) plus one badge per failed-run status, and the fastest and lightest successful backends, each tagged with its device.

Reports and exports

The report sent to the browser replaces statevectors longer than 214 amplitudes (circuits over 14 qubits) with a placeholder and sets statevector_omitted_for_display. The server keeps the untruncated report for 30 minutes after a job completes.

Accounts, history & autosave

An account is optional. Signing in (or registering with an email and password, via the Login / Register button) enables automatic run history: every completed run is saved to your account automatically, with no separate "save" step. Open Your Run History to browse past runs, rename them, download their stored reports (statevectors are removed before storage), or delete them (singly or in bulk). Without an account, results exist only in your browser for that session.

Separately, and independent of an account, the Config drawer offers autosave to a local folder: each completed run is written as a JSON file directly to a folder on your computer, with nothing uploaded anywhere. This needs the File System Access API (Chromium-based browsers such as Chrome and Edge) and degrades gracefully elsewhere.

Limitations

  • Agreement between backends is not correctness. Backends agreeing does not show they are all right, and a backend differing from the others does not show it is wrong. QRosetta has no independent reference to check against.
  • Measured-mode thresholds are descriptive. The JS/Hellinger cut-offs are configurable and depend on the shot count; measured_assessment, from the statistical test, decides whether a pair disagrees.
  • Permutation search is bounded. Exhaustive qubit-permutation matching is capped at 7 qubits. Larger cases report too_many_qubits instead of searching.
  • Timings are single samples. One warm-up and one timed run per backend; no repeat statistics are reported by default.
  • A residual disagreement is a starting point for investigation. None of the registered transforms explained the difference. The cause could be an unregistered convention, an environment limit, or a defect in a backend or its adapter.

Adding a simulator

Every runner implements the same contract: process_run (statevector) and process_run_measured (counts), built on the shared measurement instrument that does the timing, memory measurement, qubit-limit check and result assembly, so all backends are measured the same way. The step-by-step guide, including how to determine a backend's qubit ordering and how to register it, is CONTRIBUTING.md in the repository.

FAQ

Why would two correct simulators disagree?

Usually because of a convention: a different qubit ordering or an unobservable global phase. The agreement classification names these causes so that a convention difference is reported as such.

Is a "distance exceeds threshold" pair a bug?

Not by itself. It means the distances stayed above the descriptive thresholds after every registered transform. Check the pair's measured_assessment: if it is consistent_within_shot_noise, the difference is what sampling alone produces at this shot count; if inconclusive_low_shots, rerun with more shots when resolvable_by_more_shots is true; only distinguishable indicates a real difference, whose cause could be an unregistered convention, a resource limit, or a defect in a backend or its adapter.

Does QRosetta modify a backend's output?

No. Outputs are stored as each backend returned them. Bit reversal, phase alignment and permutation matching are analysis steps reported with their numerical effect. The input circuit can be changed before dispatch; every such change is listed in preprocessing_applied (see Circuit preprocessing).
