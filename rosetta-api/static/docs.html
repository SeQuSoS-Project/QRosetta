Documentation

QRosetta

QRosetta (Quantum Rosetta) runs one quantum circuit on many quantum simulators and compares their outputs pair by pair.

Overview

The input is a circuit in OpenQASM 2.0. QRosetta sends it to each selected simulator backend: Qiskit (Aer), Cirq, qsim, Qibo, PennyLane (lightning and default.qubit), Qulacs, QuEST, quimb, myQLM, PyQuil, Qrisp, cuQuantum and TorchQuantum. GET /runners lists the backends a server offers. The published release images do not include myQLM and cuQuantum, which their vendors distribute under their own licence terms; a checkout of the repository builds them, and cuQuantum also needs an NVIDIA GPU.

Every backend receives the circuit in the same request format and answers in the same result format. Several adapters parse the QASM text with pytket. The Qiskit adapter is one of them: it converts pytket's circuit with tk_to_qiskit, and its preprocessing_applied list records the pytket parse. The cuQuantum adapter, also built on Qiskit Aer, parses with Qiskit's own QuantumCircuit.from_qasm_str, so the two Aer-based backends can read the same text differently.

QRosetta compares the backends in pairs. For each pair it reports whether the outputs agree and, if they do not, whether a declared convention such as bit order accounts for the difference (Agreement classification).

The comparison is relative: apart from the self-test, which uses fixed circuits with precomputed answers, QRosetta has no reference result. A disagreement shows that at least one backend of the pair is wrong and does not say which. To decide, check the circuit against an independent reference, such as an exact calculation of your own.

A run can also send the circuit to compile-only services (eight circuit compilers). Their output circuits are recorded and shown, but neither simulated nor compared; see Compile-only services.

Quickstart: your first run

Start a local server

The README in the repository lists the host requirements (Linux on x86_64, rootless podman 4.7 or later or Docker Engine, Docker Compose v2, Python 3.11 or later) and the packages to install on Fedora, Ubuntu and RHEL. With a published release:

  1. pipx install qrosetta installs the qrosetta command.
  2. qrosetta doctor checks the host and gives the fix for each problem it finds.
  3. qrosetta pull --profile minimal fetches the API, nginx and the Qiskit, Qulacs and Cirq runners. --profile full fetches every published image.
  4. qrosetta start -d starts every service whose image is present and returns when the API is ready and the runners answer. Its last lines give the address, for example Quantum Rosetta is running at http://localhost:8080 (this computer only), followed by the addresses of this manual and of the API reference.
  5. Open that address in a browser.

qrosetta build builds the images on this computer instead of pulling them, from the build files the package carries or, in a checkout of the repository, from the working tree (./qrosetta build); the other commands are the same.

By default nginx is published on 127.0.0.1:8080, so only this computer can reach the page. When another program holds port 8080 and no address has been set, qrosetta start takes the first free port from 8081 to 8089, prints the address and keeps it until qrosetta remove. --bind ADDRESS:PORT, or QROSETTA_HTTP_BIND in .env or the environment, sets the address, for example 0.0.0.0:8080 for every interface. Publish the page beyond this computer only on a trusted network: on a local server any client may lift the circuit-size, gate-count and experiment-size limits.

A backend or compile-only service that the stack does not run, for example after --profile minimal, is struck through in the Backends and Compile-only services popovers. The first line of each popover says how many services run and gives the commands that add all of them; the row of a service that is not running gives the commands that add that one, for a backend when the pointer rests on its row (qrosetta pull for an installed release or qrosetta build for a checkout, then qrosetta start -d with its name).

Run a circuit

  1. On the first visit the editor holds a three-qubit GHZ circuit, Statevector is ticked under Mode, and every backend the server offers is selected. To start from another circuit, choose it in the Quantum Algorithms menu under Generate Circuits and press Load (see Circuit sources).
  2. Press the run button at the bottom of the left column. Its label states what will run, for example "Run Editor Code · Statevector · 14 backends". The Run choice, Mode, Run Name and the settings chips stay in view above it. During the run the results area shows the table the result will fill, with each backend's state in its Status column.
  3. Read the Summary tab. Its first line says how many backends returned a result. The next line names any backend that differs from the others, for example "Qrisp differs from all 13 other backends", and says whether the rest agree with each other; for the GHZ circuit it reads "Every comparable pair of backends agrees." The Backends table has one row per backend: status, the backends it differs from, bit order, precision, total time and peak memory. Evidence, below the table, lists the pairs by verdict.
  4. For a measured run, tick Measured. A Shots field (default 8,200) appears beside the settings chips. To make a rerun draw the same shots, open the Seed chip and enter a sampling seed, for example 42. On a circuit with many outcomes the full-distribution test may call pairs inconclusive; the Summary then gives the number of shots the test needs.
  5. The other tabs hold the detail: Agreement (a heatmap of every pair, the evidence per pair, the divergence matrices), Performance (times and memory), Circuits (the submitted, dispatched and executed text) and Exports (figures and tables, the RO-Crate and the report files).

Before and during a run

The page checks the inputs before it submits a run. If a value blocks the run (shots, timeout, seed or a threshold out of range, a Run Name with an invisible character, more circuits than the server accepts), nothing is sent: a red box above the run button, headed "Not submitted. Fix these inputs first:", lists every problem, and the field concerned is outlined in red inside its chip. The list is updated whenever the workspace changes. A request the server refuses is shown with the server's message.

While a run is in progress the Status column shows each backend's state: QUEUED (not started; no time shown), SENT, then DONE, ERROR, TIMEOUT or OFFLINE with the seconds it took. While the server compares the results (the job's phase is analysing), the progress line reads analysing results and a playlist's current circuit reads ANALYSING. For measured runs with many outcomes this step can take tens of seconds.

Stop waiting, beside the elapsed time, stops the page from waiting; the job continues on the server. The results area then reads Stopped waiting, gives the job ID and offers Show results, which waits for the job again.

If the server stops answering while the page waits (the API is restarting, or the proxy reports it unreachable), the page says it is waiting for the server and asks again after 3, 6, 12 and 24 seconds, then every 30 seconds, for up to 5 minutes. A restart of the API loses every job in progress: when the server answers without the job, the page says so, and the run has to be submitted again. After 5 minutes without an answer the page stops waiting; the job stays in this browser's list, so a reload after the server is back offers it again.

Returning to a run

The browser records every job it submits. When the page is opened again (reload, Back and Forward, a new tab), Earlier runs from this browser above the results lists the jobs whose results were not shown and the finished jobs the server still keeps (for its retention time after they finish), each with Show results and Dismiss. A job the server no longer has is dropped from the list. The list follows jobs started or dismissed in other tabs. When you are not signed in, Recent runs in the header opens and closes the list at any time. Logging out forgets the jobs submitted while signed in and clears their results from the screen.

A link of the form /#job=<job ID>, which qrosetta run, wait and selftest print, opens that job's results. The page waits for the job as Show results does, without adding it to this browser's list or saving it to an account. If the server no longer has the job, the results area says so.

Each browser tab keeps its own editor circuit, ticked modes and Run Name across reloads; a new tab starts from the values last used. The playlist, the backend selection and the export preset are shared by all tabs. The other settings (preprocessing, Bypass API Safety Limits, timeout, thresholds, seed) return to their defaults when the page loads. Below 1024 pixels of width the workspace, the Run footer and the results follow each other in one column. A table wider than the results panel scrolls sideways, with a shadow on the side that has more columns.

Circuit sources

The left column has three panels: Generate Circuits offers ready-made circuits, the Editor holds the circuit you are working on, and the Playlist holds circuits to run together.

  • Generate Circuits. The Quantum Algorithms menu lists four groups: the generated algorithms (GHZ, Bell, QFT, Bernstein–Vazirani, Grover, VQE ansatz, random, bit-order probe), the bundled Examples (GET /examples), MQT Bench algorithms and QASMBench circuits. Typing in the menu searches all four. For an algorithm or an MQT Bench algorithm, Qubits sets the size; an MQT Bench size moves to the nearest size the suite has. Examples and QASMBench circuits have a fixed size. The line under the menu describes the selection, and for an example names the mode it is meant for. Load puts the selection in the editor, asking first if that would replace your edits; loading an example also ticks its mode. + Add adds the selection to the playlist.
  • Editor. Type or paste OpenQASM 2.0. Import QASM reads a file into the editor and Export QASM saves its text. + Add to Playlist adds the editor's circuit to the playlist under the name above the editor.
  • Playlist. Quick Load adds a ready-made set (Sanity Check: every algorithm at 5 qubits; Scaling Test: GHZ from 5 qubits to the statevector limit; Memory Stress: random, Bernstein–Vazirani and VQE circuits at the statevector limit; the sets come from GET /quickload). Auto-Gen adds circuits of the chosen algorithms at random qubit counts, up to the limit of the ticked modes (the statevector limit while Statevector is ticked) and each algorithm's own maximum, and says when it lowered a count. Clear asks before it empties the playlist. Bench opens a list of MQT Bench or QASMBench circuits with a name filter and a qubit cap; tick circuits and add them, or add every circuit the list shows (with no filter and no cap, the whole suite). Escape or a click elsewhere closes the list. The playlist can be exported to a JSON file and imported again.

Run, in the footer of the left column, switches between Editor code and Playlist. Loading a circuit into the editor selects Editor code; adding to the playlist selects Playlist. A warning appears in the footer when a circuit has more qubits than a ticked mode allows, and when a measured circuit has more than 22 qubits, where several backends are likely to reach the timeout. A 24-qubit QFT of 340 gates did not finish within 300 s on 7 of 14 backends; a 24-qubit circuit of 94 gates finished on all 14 within 300 s, 3 of them after more than the default 60 s.

Run modes

ModeWhat each backend returnsHow QRosetta compares
Statevector The amplitudes of the final state, without sampling. Fidelity and global phase offset arg⟨a|b⟩ of each pair of normalised states. No seed is used.
Measured A histogram of measurement outcomes over a given number of shots. A shot-noise test of each pair, with the Jensen–Shannon divergence (in nats) and the Hellinger distance of the two distributions, each normalised by its observed total, as descriptive distances.

Statevector runs are limited to 18 qubits and measured runs to 24, because a full statevector grows as 2n; a compile-only run builds no statevector and has a limit of 24 qubits. GET /config reports the limits. Each backend's run ends with one of four dispatch statuses: ok, error (the backend rejected the circuit or failed), timeout (the run exceeded the timeout, or never left the runner's queue; see Resources, queueing and timeouts) or offline (the runner could not be reached). The timing and memory fields of a failed run are null, and every pair that includes it is not comparable.

Circuits the API refuses

Before a run starts, the API checks the text and refuses it with HTTP 400, giving the line, when it finds any of the following:

  • a header other than OPENQASM 2.0; (the short form OPENQASM 2; included)
  • a non-ASCII character outside a comment (the message gives its column and Unicode name, for example a non-breaking space), or a control character other than tab and line break
  • a semicolon with no statement before it
  • a name declared twice among registers, gates and opaque gates, which share one set of names; with include "qelib1.inc"; the qelib1 gates belong to that set, so qreg x[1]; or creg h[1]; is refused
  • an index outside its register, an operand that is not a declared register, or a classical register given to a gate
  • a call of a gate that neither the circuit nor an included qelib1.inc defines (names are case-sensitive: H and cnot are not qelib1 gates)
  • a call with the wrong number of parameters or qubits, such as cx q[0]; or rx q[0];, or one that names a qubit twice, such as cx q[0],q[0]; or cx q,q[0];
  • a broadcast over registers of different sizes, such as cx a,b; with a[2] and b[3], or a measure whose two sides differ in size, such as measure a[0] -> c; with c[2]
  • a register name that does not start with a lowercase letter, such as qreg Q[1];, and a gate or register used before its declaration
  • a name in a parameter inside a gate definition that is not one of that gate's parameters, such as gate g a { rz(t) a; }
  • a /* ... */ comment (OpenQASM 2.0 has only // comments)
  • a top-level call that reaches an opaque gate, directly or through gate definitions. An opaque gate has no definition, so no simulator can apply it; declare it with gate and a body instead. An unused opaque declaration is accepted, and the pytket round-trip drops it.

Spaces between a register and its index (q [0], q[ 0 ]) are legal. The pytket round-trip does not accept them, so with SDK preprocessing on the API removes them and records an API: entry. Gate parameters may have any name, including lambda, as in qelib1.inc. Input limits, under Run options, lists the size limits.

Measurements, reset and classical control

In statevector mode the API removes the measurements at the end of the circuit and records an API: entry in preprocessing_applied. A circuit with a measurement followed by further operations, a reset or an if has no single final statevector, so statevector mode refuses it with HTTP 400; run it in measured mode. A compile-only run accepts such a circuit and records each requested compile as skipped.

In measured mode these operations go to every backend, and an adapter that cannot simulate them returns an error for its backend. Qiskit and cuQuantum (Aer) run mid-circuit measurement, reset and if; Qrisp runs mid-circuit measurement and if; Cirq and qsim run mid-circuit measurement. The other backends refuse all three.

Device and precision

A result can report device (CPU or GPU), simulator_backend (the library that executed the circuit) and simulation_method; the Summary's Run details per backend and the Performance tables show them as tags. Qiskit runs on qiskit-aer's AerSimulator with method="statevector". The cuQuantum backend is qiskit-aer-gpu 0.15.1 with cuStateVec enabled, on an NVIDIA GPU; its results also carry gpu_name and custatevec_enabled. On a server without a usable NVIDIA GPU, cuQuantum is listed as unavailable in the Backends popover, with the reason the server gives, and is not dispatched; it never falls back to the CPU. Its kernels run on the GPU, and its host-side work (parsing, kernel launches, copying results back, sampling) runs under the same CPU quota as the other runners (Resources, queueing and timeouts). A time comparison between cuQuantum and a CPU backend therefore compares different hardware.

Each backend reports the precision of its amplitudes. qsim, Qrisp, TorchQuantum and Cirq's measured path compute in complex64, the others in complex128; cuQuantum reports the precision its simulator was configured with. The report tabs show a precision badge per backend. The fidelity of a complex64 backend against a complex128 one includes single-precision rounding error.

Circuit preprocessing

The circuit can be changed in two places, the API and the runner. Every change is recorded in each backend's preprocessing_applied list.

In the API (entries beginning API:, tagged API on the page). The API prepares one circuit per dispatch group. Measured mode has two groups: measured_native, backends that sample with their own sampler, and measured_sampled, backends whose final statevector is sampled. With Apply SDK Preprocessing on, the API merges several quantum registers into one in declaration order and passes the circuit through pytket (parse, then write), which removes barriers; in statevector mode it first removes the final measurements.

The pytket round-trip inlines custom gate definitions, expands register broadcasts and writes the gates in pytket's QASM gate set, with angles as multiples of π. pytket 1.33 writes u as u3, p as u1 and u0 as u3(0,0,0); it decomposes cp into three u3 and two cx, cu into five u3 and two cx, and rccx, rc3x and c3sqrtx into u3 and cx. It keeps cu1, crz, crx, cry, cu3, ch, cy, csx, rxx, rzz, ccx, cswap, c3x and c4x as written. tket sets a parameter within 1e-11 half-turns of a multiple of π/4 to that multiple; the API: entries list each parameter moved in this way.

In measured mode the native group also receives a measurement of every qubit when the circuit has none (see Counts keys); this happens with preprocessing off too. With preprocessing off there is no register merge and no pytket round-trip in any group, and statevector mode still removes the final measurements. The report's dispatched_circuits lists which runners were in which group.

In the runner. Each backend applies its own passes: gate rebasing, barrier removal, and the SDK's default compilation pass at every optimization level. Passes that the adapter applies in every case say so in their text. The Qibo and quimb QASM parsers lack some qelib1.inc gates (ch, cswap, c3x, c4x, rccx, rc3x, c3sqrtx and u0 for Qibo; u, p, ch, csx, cp, cu, rccx, c3x, c3sqrtx, rc3x and c4x for quimb). With preprocessing on, these two adapters insert the qelib1.inc definitions (Qiskit 2.5.2's copy) of the gates a circuit uses and list them; for quimb the built-in U in those definitions is written as u3. With preprocessing off these gates are refused.

The RO-Crate stores the circuit as submitted (circuit.qasm), the circuit the API sent to each runner (dispatched_circuits/<runner>.qasm; <circuit>/<runner>.qasm in a playlist crate) and the circuit each backend executed (transpiled_circuits/). A playlist crate or an experiment bundle that includes bundled MQT Bench or QASMBench circuits also holds that suite's licence under licenses/.

Run options

The settings chips above the run button (Backends, Execution, SDK Preprocessing, Compile-only services, Agreement Thresholds, Seed) each show the current value, are filled in indigo when it differs from the default, and open their controls in a popover. The settings apply to single runs, playlist runs and experiments alike. Each has an API field of the same meaning, listed in the Swagger UI at /docs.

  • Timeout per backend (timeout_seconds, Execution chip, 10 to 300 s, default 60 s) covers start-up, warm-up and every timed run; Resources, queueing and timeouts describes its scope.
  • Timing repeats (timing_repeats, Execution chip, 1 to 10, default 1) is the number of timed runs per backend after one discarded warm-up run. All of them run in one process and give one result per backend. With more than one, the result carries compilation_time_samples and simulation_time_samples with their mean, median and standard deviation, timing_samples (the number of timed runs) and timing_statistic: "median"; the Performance tab shows the median ± the sample standard deviation with n. The warm-up and all repeats share one timeout. To compare separate runs of one backend with each other, use multi-run mode (below).
  • Exclusive timing run (exclusive, Execution chip, default off). The backends run one at a time, each in its own phase, and the job runs only while no other run is in flight on this server: it waits for running jobs, and jobs submitted meanwhile wait for it. Results record exclusive and exclusive_wait_sec. Every result records gate_wait_sec, so a job held back by another user's exclusive run shows how long it waited; its runners show as queued meanwhile. When an exclusive run ends, the jobs it held back start together and overlap each other (server_overlapping_runs). If runner_phases gives every backend a different phase, that order is kept; otherwise the backends run in order of their ids. Reports record the phases used as effective_runner_phases. The option cannot hold back other programs on the host, and in Kubernetes mode it covers only this server's runner Jobs. Each client may have one unfinished exclusive job; a second returns HTTP 429. An exclusive circuit that cannot start within the server's wait cap (exclusive.max_wait_sec in GET /config, default 600 s) fails with that reason. GET /config also shows whether an exclusive run is running or waiting, and operators can turn the option off with QROSETTA_EXCLUSIVE_ENABLED=false.
  • Shots (n_shots, measured mode, default 8,200; the field appears beside the chips when Measured is ticked). With 14 backends, 8,199 shots per backend give the power model 0.8 on circuits with up to 16 outcomes. Circuits with more outcomes need more shots, and the Summary recommends a count when it can.
  • Multi-run mode (self-comparison), in the Backends popover, runs one backend several times, each run in its own process, at the same or different optimization levels, and compares the runs with each other as if they were separate backends. In the API a list in runner_config runs that backend once per element, for example {"qiskit": [0, 0, 1]}. Each run gets the key <runner>~opt<L>~run<N>, which also enters its seed derivation. A request may ask for at most 16 runs of one backend and 48 runs in total; more is refused with HTTP 422. In the popover each count must be a whole number; while a count is not, or the counts exceed these limits, the popover and the Run footer say so and the run button is disabled.
  • Custom ordering (phases) (runner_phases), in the Backends popover, gives each backend a phase number. Backends with the same number run at the same time, and phases run in ascending order. In measured mode the phases cover both groups of backends (sampled statevector and native sampling): phase 2 of either group starts only after phase 1 of both has finished. Without phases every backend runs at once. Phases decide which backends share the host at the same moment; the CPU quota of each runner stays the same.
  • Apply SDK Preprocessing (apply_preprocessing, SDK Preprocessing chip): On, Off, or Both, which runs an experiment (Several circuits and experiments). Circuit preprocessing describes what it changes.
  • Bypass API Safety Limits (bypass_limits, SDK Preprocessing chip) lifts the playlist length limit and, for an experiment, the limit on circuits × preprocessing settings. On a local server it also lifts the QASM size limit and the statement-count limit. The request-body limit, the qubit limits, the expanded-gate and nested-gate-call limits (which protect the runners' memory), the preparation limits, the syntax checks and the measurement checks always apply. On a local server anyone may set the option. On any other server only a signed-in account may (bypass_limits_requires_account in GET /config): a request without a valid sign-in is refused with HTTP 401, and the page disables the option while you are signed out. The report records the setting.

The bit-order probe

The Bit-order probe algorithm (2 qubits or more) applies x to qubit 0 and a different ry angle to every other qubit, so its output changes under every qubit permutation. It shows each backend's declared bit order directly: an lsb backend and an msb backend agree on it only after the bit reversal their declarations imply.

Input limits

  • At most 18 qubits in statevector mode, 24 in measured mode and 24 in a compile-only run, counted over every qreg declaration.
  • At most 1,000,000 characters of QASM text (HTTP 413 above). Separately, every request body, including POST /export, may hold at most 1,048,576 bytes (1 MiB, limits.max_request_bytes). That limit counts the JSON as sent, in which every line break and quote of a circuit takes two bytes, and a playlist sends all its circuits from the editor or from files in one request. The page checks both limits before it sends a run and names the circuit or request that is too large; split a large playlist and run the parts one after another.
  • Run, circuit, task and author names hold at most 200 characters (limits.max_label_length), without control characters, invisible formatting characters or line separators. The page removes such characters and shortens longer names before it sends them.
  • At most 10,000 operation statements (gates, measure, reset, barrier, if; max_qasm_gates in GET /config), counted at top level and inside gate definitions; a definition with an empty body counts as one. The header, the include line and register declarations are not counted.
  • At most 1,024 classical bits over all creg declarations (limits.max_classical_bits). Every register holds at least one qubit or bit, and a gate parameter has at most 1,000 characters. OpenQASM keywords (gate, measure, pi, sin, ...) cannot name a register or gate. A // comment that contains /* needs a */ after it on the same line.
  • At most 200,000 gate applications after user gate definitions and register broadcasts are expanded (limits.max_expanded_gates), and at most 4,096 applications of user-defined gates made from inside gate definitions (limits.max_nested_gate_calls; top-level calls are not counted). The first limit stops a short circuit of nested definitions from expanding to millions of gates. The second exists because several parsers keep a copy of a nested definition for every application: eleven levels of definitions that each call the level below twice (4,094 nested applications) peaked at about 710 MiB in the PennyLane runners and twelve levels at about 1,090 MiB, while 8,192 top-level calls of one definition took about 340 MiB. The bundled benchmark circuits are exempt.
  • With apply_preprocessing on, the API prepares each circuit (the pytket round-trip) in a separate process limited to 1,024 MiB and 120 s (limits.prep_max_mib and limits.prep_timeout_sec; server settings QROSETTA_PREP_MAX_MIB and QROSETTA_PREP_TIMEOUT_SEC). A preparation that exceeds either is stopped, and the run fails with a message naming the limit and its value; with apply_preprocessing=false the text is dispatched without the round-trip. The memory a preparation needs cannot be read from the circuit text, so only circuits whose preparation has been measured are refused in advance. Among the bundled circuits, the MQT Bench Grover circuits exceed the memory limit from 15 qubits: grover-noancilla needed about 1.5 GiB and grover-v-chain about 1.2 GiB at 15 qubits, and both more than 2 GiB from 16 and 17 qubits respectively; every other bundled circuit stayed under 400 MiB. GET /config lists the bundled circuits over the server's limit as bundled_over_prep_limit. A run that includes one of them with preprocessing on is refused with HTTP 400 naming the circuit, and the page says so before it sends the run. Written-out versions of these circuits are refused earlier, by the expanded-gate and nested-gate-call limits.
  • A playlist run holds at most 400 circuits (limits.max_batch_tasks), enough for both bundled suites (269 MQT Bench and 55 QASMBench circuits) in one playlist. A longer playlist is refused with HTTP 400, and the page says so before it sends the run; split it and run the parts one after another.
  • A custom gate or opaque name that a backend's QASM parser reserves for its own operations (pytket, Qiskit, myQLM, Qibo and quimb each have such names, for example sleep, fsim and iswap) is refused with HTTP 400 in every mode, whichever backends are selected, so that every backend receives the circuit as written. The message names the gate and the line of its definition; rename the gate.

Quirk visualizer

The editor's Visualize button converts the editor's circuit to Quirk's JSON format (POST /visualize/quirk) and opens it in Craig Gidney's Quirk, an external web page, in a frame that covers the window. Open in Quirk (the same page in a new tab) and Close sit above the frame. Escape also closes it, except while the keyboard focus is inside the Quirk frame, where Quirk receives the key; Tab out of the frame or use Close. On a phone or tablet Quirk's page scrolls sideways inside the frame.

The circuit is checked as for a run, its registers are merged in declaration order, and pytket parses it. Gates that have a Quirk symbol keep it: H, X, Y, Z, S and T (as Z^½ and Z^¼) and their inverses, sx as X^½, rx, ry, rz, u1 and p as X^t, Y^t and Z^t with the angle in half-turns, cx, cy, cz, ch, ccx, c3x and c4x as controls, swap and cswap. Every other gate is drawn as cx and single-qubit Z^t and Y^t rotations with the same matrix up to a global phase, and the response's notes name those gates. Final measurements are drawn in a last column; barriers are not drawn. The visualizer opens at most 16 qubits (Quirk's own limit) and 1,000 columns, and refuses reset, if and a gate after a measurement of the same qubit, with the reason.

Experiments: preprocessing on and off

With SDK Preprocessing set to Both, each circuit runs once with preprocessing on and once with it off. The result is one ZIP bundle, in a top-level folder named experiment_<label>, or experiment_ followed by the first eight characters of the job ID when there is no label. It contains:

  • inputs/<circuit>.qasm: the QASM of every circuit as it was at run time;
  • results/<setting>/<circuit>.json: the report of each circuit and setting;
  • conformance_matrix.csv: whether each circuit ran on each backend. Every error row carries the marker untriaged, for you to classify as an adapter issue, an SDK issue, by-design behaviour or a resource limit; the software does not classify errors. errors/<backend>.log holds the error texts;
  • agreement_prevalence.csv: how many backend pairs fell in each class, by measured_assessment in measured mode and by label in statevector mode;
  • performance.csv and a README.txt that explains the files;
  • manifest.json: the git commit, the executed SDK versions, the seeds used and the effective configuration. config_sha256 and effective_config_sha256 are the sha256 of json.dumps(config, sort_keys=True, default=str) in Python, encoded as UTF-8 (separators ", " and ": ", non-ASCII characters escaped);
  • runners/<runner>/requirements.lock: each runner's pinned environment, under the same rule as in an RO-Crate.

In the API the experiment is POST /experiments with a list of circuits and preprocessing_modes ([true], [false] or [true, false]); the bundle is GET /experiments/{job_id}/bundle. The bundle is written to the API's local disk as the cells finish and is deleted with the job, at the latest after the job's retention time. Experiments are not saved to the run history. One experiment runs at most 200 combinations of circuit and preprocessing setting (limits.max_experiment_cells in GET /config), so Both takes at most 100 circuits; a larger request is refused with HTTP 400 before it starts, and the page says so before it sends it.

Compile-only services chosen together with Both run with the first experiment of the press of Run (the statevector one when both modes are ticked), once per circuit and setting. That experiment's panel lists them, and its bundle holds the outputs under compiled_circuits/<setting>/<circuit>/ and in compiled_circuits.csv; the other experiment's panel says where they are.

Agreement classification

Two correct simulators can return outputs that look different, because they order qubits differently (endianness) or differ by an unobservable global phase. For each pair of backends, QRosetta tries a fixed list of transforms in order and reports the first under which the two outputs agree, with the metric before and after it.

A statevector pair agrees when its fidelity, computed on normalised vectors and stored unrounded, is at least 1 − fidelity_tolerance. The default tolerances are fidelity_tolerance = 1e-5, phase_tolerance = 1e-6 rad, norm_tolerance = 1e-4, js_threshold = 0.01 nats and hellinger_threshold = 0.1; GET /config reports the server's defaults. The Agreement Thresholds chip changes them. The values sent are recorded in the report's run configuration and in every pair record, and the pair record holds the values its label was computed with. The phase tolerance of 1e-6 rad lies above single-precision rounding (about 1e-8 rad for complex64), so rounding alone does not make a complex64 backend appear to carry a global phase.

Metric formulas

Statevectors

Each backend's statevector a is normalised first: â = a / ‖a‖₂. The norm ‖a‖₂ is recorded in metrics.norms; if |‖a‖₂ − 1| > norm_tolerance for either side, the pair is flagged unnormalized_input.

  • Direct fidelity: F = |⟨â|b̂⟩|² = |Σₖ conj(âₖ) b̂ₖ|², clamped to [0, 1] and stored unrounded.
  • Global phase offset: φ = arg⟨â|b̂⟩ in radians, in (−π, π]; a value with |φ| ≤ phase_tolerance is reported as 0. This is the overall phase between the two states. A relative phase between components of a superposition lowers the fidelity instead. The JSON field is direct_relative_phase_rad and the matrix is relative_phase_matrix.
  • Bit-reversed fidelity: F_rev = |⟨â|R b̂⟩|², where (R b)ₖ = b_rev(k) and rev(k) reverses the n-bit binary representation of the index k.
  • Permutation fidelity: the largest |⟨â|P_π b̂⟩|² over every permutation π of the n bit positions other than the identity and the reversal; P_π reshapes the vector to n axes of size 2 and transposes them by π. Ties keep the lexicographically first permutation. The search runs for n ≤ 7 qubits; above that the pair records too_many_qubits.

Let ε = fidelity_tolerance and let F_al be the label-aligned fidelity (F in the direct basis, F_rev in the bit-reversed basis; recorded as metrics.label_aligned_fidelity). Labels are assigned in this order. In the direct basis, agree_directly if F ≥ 1 − ε and |φ| ≤ phase_tolerance, else agree_up_to_global_phase if F ≥ 1 − ε; in the bit-reversed basis, agree_after_bit_reversal if F_rev ≥ 1 − ε. Otherwise, residual_disagreement with unaligned_basis_match if the fidelity in the other basis is ≥ 1 − ε; else agree_after_qubit_permutation if the permutation fidelity is ≥ 1 − ε; else residual_disagreement. An agreeing pair with unnormalized_input is relabelled agree_after_normalization. The Summary quotes the fidelity under the transform the label names, with the direct fidelity beside it.

Counts

Each backend's counts c(x) are normalised by its own observed total, p(x) = c(x) / Σₓ c(x), over the union of the two backends' outcomes.

  • Jensen–Shannon divergence: JS(p, q) = ½ Σ p ln(p/m) + ½ Σ q ln(q/m) with m = (p + q)/2 and the natural logarithm, so it is in nats and lies in [0, ln 2 ≈ 0.693].
  • Hellinger distance: H(p, q) = (1/√2) ‖√p − √q‖₂ = √(1 − Σ √(p q)), in [0, 1].
  • Total variation distance: TV(p, q) = ½ Σ |p − q|, in [0, 1]; recorded as statistical_test.effect_size.total_variation.

A measured pair is distance_within_threshold when JS ≤ js_threshold and H ≤ hellinger_threshold; the bit-reversed and permuted counts are tried next, as for statevectors.

Shot-noise tests

The table. The two backends' counts form a 2 × K contingency table O over the K outcomes either backend observed; outcomes with no counts on either side are dropped. The table is built in the label-aligned basis: when the two backends declare different bit orders (lsb against msb), the second backend's keys are bit-reversed first; otherwise the keys are compared directly. The basis follows the declared orderings, even when the other basis gives a smaller distance, and is recorded as statistical_test.basis. With keys of one classical bit, bit reversal changes nothing, and the keys are compared directly (basis_source: "single_bit") whatever the number of qubits. With row totals Rᵢ, column totals Cⱼ and N = Σ O, the expected counts are Eᵢⱼ = Rᵢ Cⱼ / N.

Rare outcomes. Outcomes whose expected count is below 5 are pooled into one bin, which holds only rare outcomes; pooled_outcomes records how many when the bin holds two or more (a bin of one outcome is an ordinary column and records 0). The bin is tested as a column of its own when its expected count is at least 5, when the table meets Cochran's rule (no expected count below 1, at most 20% below 5), or, with two or more common outcomes, when its expected count is at least 1. Below 1 the bin is left out of the table (untested_outcomes). A common outcome is never merged into the bin: on a table of three or four outcomes that would hide a gap as large as the common outcome's probability (see the power model below).

Exact conditional p-values. A 2 × 2 table that still fails the expected-count rule (one common outcome beside an undersized bin, as for a near-deterministic circuit whose rare outcome has probability 10−4, or exactly two observed outcomes, both rare) is outside the range of the chi-square approximation. Both statistics then get exact conditional p-values (test_method: "exact_conditional", chi2.method, g_test.method): with the shots and the column totals fixed, the first backend's count in the second column is hypergeometric, and each p-value is the probability of a table whose statistic is at least the observed one. With equal shot totals this ordering gives the same p-value as Fisher's exact test. With unequal totals the two can differ: for rows of 100 and 37 shots, [[99, 1], [36, 1]], p = 1.0 here and 0.469 by Fisher's test, which orders tables by their probability. With three or more observed outcomes, all rare, the pair is inconclusive (low_expected_counts). When both backends returned the same single outcome there is nothing to test: the statistics are 0, the p-values 1, and test_method is "degenerate" ("not_tested" when pooling leaves one column, which is also a low-count case). The Summary says how many pairs have exact conditional p-values and how many were degenerate, and each pair's details give its method.

  • Pearson chi-square: χ² = Σ (O − E)² / E, no continuity correction, df = K − 1.
  • G-test: G = 2 Σ O ln(O / E) divided by Williams' correction q = 1 + (N Σ 1/Rᵢ − 1)(N Σ 1/Cⱼ − 1) / (6 N (rows − 1)(K − 1)), same df (g_test.statistic; the uncorrected value is statistic_uncorrected and q is williams_q). Without the correction the G-test rejects far too often on tables with many bins of small expected counts. In a simulation with no real difference (2,000 tables of 65,536 outcomes at 106 shots, scripts/verify/v8_calibration.py), the uncorrected G-test rejected 94.7% of tables at α = 0.05, the corrected G-test 6.2% and the chi-square test 4.2%.
  • Cramér's V: √(χ² / N).
  • Multiple comparisons, over the m tested pairs of the run, for each test separately. Benjamini–Yekutieli (correction: "BY"): with p-values sorted p₍₁₎ ≤ … ≤ p₍ₘ₎ and c_m = Σᵢ₌₁..ₘ 1/i, p̃₍ₖ₎ = min over j ≥ k of min(1, m c_m p₍ⱼ₎ / j), recorded as p_value_by. A test is significant (significant_by) when its BY-adjusted p-value is below α = 0.05. BY controls the false discovery rate at q = α under any dependence between the tests; pairs that share a backend share its sample, so their tests are dependent. Up to a fraction q of the pairs BY flags are expected to be flagged by chance, and one unusual sample of one backend can flag several of its pairs at once. The Benjamini–Hochberg (p_value_bh), Bonferroni (min(1, m p), p_value_bonferroni) and Holm step-down (p_value_holm, significant_holm) adjusted p-values are recorded as well; Holm's controls the family-wise error rate. A distinguishable pair carries significant_fwer, true when both tests also pass Holm. Under BY, real differences in other pairs lower the threshold for every pair. With one backend among 14 wrong by a total variation of 0.40 (2 to 16 outcomes, 8,200 shots), at least one pair of two correct backends was flagged in 7.3–9.4% of simulated runs, and by a flag that also passes Holm in 3.2–4.3%; with every backend correct, 0.6–1.1% of runs had any flag (scripts/verify/false_flags.py, 2,000 to 4,000 runs per scenario). The Summary marks a distinguishable pair that fails Holm as significant under BY only. A p-value that underflows to 0 is shown as <1e-300, and values below 1e-3 in scientific notation.
  • Verdict: inconclusive_low_shots (low_expected_counts) if no pooling gives adequate expected counts and the table is larger than 2 × 2; else distinguishable if both tests are significant, ambiguous if exactly one is, and, if neither is, consistent when the power at the observed shots, computed at α/(m·c_m), is at least 0.8 and inconclusive_low_shots (low_power) otherwise.
  • Shot advice: resolvable_by_more_shots, beside inconclusive_reason, says whether more shots can turn an inconclusive pair into a verdict. It is null, and no shot count is recommended, when the sample does not characterise the outcome distribution: unseen_mass_good_turing, the share of shots in outcomes seen exactly once (the Good–Turing estimate of the probability of outcomes not yet seen), exceeds 0.5 for either backend (support_characterised: false). This happens when a circuit spreads its outcomes over far more basis states than the shots cover, for example a dense 22-qubit state at 8,200 shots; measuring only the qubits of interest gives the test a distribution it can resolve. When the unseen mass is between δ/2 and 0.5, the recommendation is a lower bound (recommendation_is_lower_bound), because more shots reveal new outcomes and can raise it. It is also a lower bound when the recommendation comes from pooling rare outcomes and some outcomes were seen once: outcomes seen once in n shots stop being pooled at 10n shots per backend, so the minimum often lands there (82,000 for a 12-qubit circuit at 8,200 shots, recommended as 91,000), and outcomes not yet seen do not enter the calculation. For a 12-qubit QFT at 8,200 shots the minimum was 84,838, and at 100,000 shots every pair was consistent.
  • Power model: the effect size is Cohen's w = δtested, the smallest w that any pair of distributions at total variation δ = 0.05 can have on the table the test sees (w ≥ TV). Pooling two or more rare outcomes into one bin can hide up to min(P, Q) of the total variation, where P and Q are the two backends' probabilities in the pooled bin, so δtested = δ − min(P, Q); leaving a bin out can hide up to max(P, Q), so δtested = δ − max(P, Q) (recorded as power.delta_tv_tested and power.pooled_probability). The bin holds only rare outcomes, so P and Q are small whenever the table has common outcomes. When δtested ≤ 0, a gap of δ could lie entirely inside the pooled bin; the power is then α′, and the pair is inconclusive however small its p-values. Otherwise the chi-square statistic follows a noncentral χ² with df = K − 1 and noncentrality λ = 4·ni·nj/(ni + nj) · w², where ni and nj are the two backends' shot totals. With equal totals this is N w² (N = ni + nj); with unequal totals the smaller sample limits it, so 8,200 shots against 50 have the power of about 200 shots split evenly. The single-bit marginal tests use the same noncentrality. power_to_detect_delta_at_observed_shots = 1 − F(χ²₁₋α′,df ; df, λ) with α′ = α/(m·c_m), the level BY applies to a single discovery among the m tested pairs of the run (recorded as power.alpha_used, power.m_pairs and power.c_m). It is the smallest level BY applies to any pair, so the power figure does not overstate the chance that the corrected test flags a gap of size δ. It is the power of the chi-square test alone, while the verdict needs both tests to be significant. Pairs tested with exact conditional p-values use the same model, because at the alternatives it describes the counts are large and the asymptotic test applies. In simulation (P(rare) = p₀ against p₀ + δ, 14 backends of which one differs, 2,002 differing pairs each, m = 91), both tests at α′ detected δ = 0.05 at 4,444 shots per backend in 100% of pairs for p₀ ≤ 0.1 and in 79.2% for p₀ = 0.475, against a model power of 0.800; BY over the run, in which the other 12 pairs of that backend also differ, flagged 93.1%. The shots needed therefore grow with the number of outcomes (df) and with the number of backends (m), and the report computes the power of each pair. shots_per_backend_for_target_power is ⌈N*/2⌉, where N* is the total that gives power 0.8 at α/(m·c_m); when outcomes were pooled, it is the smallest count at which the observed proportions, scaled to that count, pool into a table with that power. recommended_shots_per_backend is that minimum times 1.1 (recommendation_margin), rounded up to two significant figures and capped at the platform maximum. A rerun estimates the power again from its own table, whose bins change with the shot count, so a rerun at exactly the minimum lands near 0.8. In simulation (5-qubit product state, 14 backends, 8 runs advised from 1,000 shots), 67 of 728 pairs stayed inconclusive at the minimum (about 10,000 shots) and none at the recommended 11,000. recommended_exceeds_actual says whether the recommendation is more than the shots either backend used; the Summary recommends more shots only then. Because df counts the observed outcomes, the recommendation can be too small when the true support is larger.

Counts keys

A counts key is a bitstring over every classical bit the circuit declares, including bits that no measure statement writes; those read 0. Classical bits get one flat index in creg declaration order: with creg c[2]; creg d[3];, c[0] and c[1] are bits 0 and 1 and d[0]…d[2] are bits 2–4. In an lsb key classical bit 0 is the rightmost character; in an msb key it is the leftmost.

A circuit without measurements, run in measured mode, gets a measurement of every qubit for the backends that sample natively (see Circuit preprocessing): a new register named meas (meas0, meas1, … if that name is taken), declared after the circuit's own registers, with qubit k read into meas[k]. Backends whose final statevector is sampled read out the same register, so every key holds the declared classical bits (all 0) followed by meas.

The shot-noise statistical test

In measured mode a fixed distance threshold describes a pair but cannot judge it: with few shots, two samples of the same distribution can differ noticeably. Beside the JS/Hellinger label, QRosetta therefore reports for every comparable pair:

  • a Pearson chi-square test (no continuity correction) and a Williams-corrected G-test of homogeneity between the two count vectors, in the basis the two backends' declared bit orders select, with rare outcomes pooled;
  • Benjamini–Yekutieli adjusted p-values across all pairs of the run (false discovery rate control under any dependence), which decide significance, with Benjamini–Hochberg, Holm and Bonferroni adjusted values recorded beside them;
  • the effect size (total variation, Cramér's V) and the power to detect a total variation of 0.05 at α/(m·c_m), on the observed degrees of freedom (power.df).

The verdict is consistent, distinguishable, inconclusive_low_shots or ambiguous, from the BY-adjusted p-values at α = 0.05 and the power; Metric formulas gives the statistics, the corrections and the power model. Each backend samples with its own derived seed, so no two backends draw the same shot sequence; shared_seed records whether a pair's runner seeds were equal.

Single-bit marginals

A circuit with many outcomes often gets inconclusive_low_shots at the default shots, because most outcomes are seen only a few times. As a second, separate analysis, every pair whose keys have two or more bits is also compared bit by bit: for each classical bit, the two backends' counts of that bit being 0 and 1 form a 2×2 table, tested with the same chi-square and Williams-corrected G-test. All bit tests of all pairs form one family under Holm's correction at α = 0.05, so the probability of any false flag in a report is at most α however many backends really differ. A bit differs when both tests are significant. A bit with an expected count below 5, or constant in both samples, is not tested. Equal distributions have equal marginals, so a differing bit shows that the two distributions differ; marginals that do not differ leave the question open.

The full-distribution tests and the marginal tests are two families, each at α. Each pair records marginal_assessment (marginal_distinguishable, no_marginal_difference_detected, not_tested or not_applicable) and metrics.marginal_test (each bit's P(1) on both sides, raw and Holm-adjusted p-values). The marginal analysis leaves measured_assessment unchanged, so a pair can be consistent_within_shot_noise (no total-variation gap of 0.05 found) and still have a differing marginal. The Summary lists such pairs in a block of their own, the Agreement tab marks them "marginal differs", playlist badges count them as anomalies, and crates and experiment bundles count them by marginal_assessment.

In a simulation with 14 backends, 16 independent bits and 8,200 shots (scripts/verify/false_flags.py), 4.5% of 8,000 runs had a false marginal flag when every backend sampled the same distribution. With one backend off by 0.05 in P(1) on four bits, 4.6% of 2,000 runs had a flag on a pair of correct backends, and every pair with the wrong backend was flagged. With every backend correct, the two families together flagged at least one pair in 3.9–4.8% of runs (keys of 2 to 4 bits), against 0.6–1.1% for the full-distribution test alone.

Reproducibility

  • Seeds. Every measured run has a master seed: the one entered in the Seed chip, or one the API generates; the report records it at seed. Each backend receives runner_seed = the first 4 bytes of sha256("<master seed>:<runner key>"), read big-endian, with the top bit cleared; the runner key includes any ~opt<L>~run<N> suffix. The report records the formula at seed_derivation. seed_honoured is false for a backend whose sampler ignores the seed (Braket, which is disabled). In a playlist every circuit uses the same master seed, so each backend receives the same runner_seed for every circuit.
  • SDK versions. Each backend reports the versions of the SDK packages it executed with, and the report keeps them in its provenance.
  • The image each backend ran from. Every runner and compiler result carries image_identity. The runner's serving process reads it at startup from a file in the image and adds it to each result after the run returns. It holds:
    • the source the image recorded at build: release for an image built by the release pipeline, built_locally for a local build, "not recorded" for an image built before images recorded it; then the release and the commit;
    • what the container runtime shows the process: Apptainer's image path and sha256, or a podman container's image and id (the latter only when privileged);
    • whether the host CPU reports the hypervisor flag;
    • emulation: the machine the image's Python interpreter is built for (read from its ELF header), the host's OS and machine as qrosetta start passed them, and emulated, true when the two machines differ and null when the stack was started without qrosetta start.
    build_files holds the sha256 of the Dockerfile and the requirements.lock the image copied. runner_image is the image the API created a Kubernetes Job with, else the image the runtime showed the runner; runner_image_basis says which. Each result that ran gets a specimen, and the report a specimens summary: all_published (one release), all_built_locally, mixed, unknown or none_ran, with each backend's detail and the image commits. Differing commits mean the measurement code may differ between backends. An RO-Crate includes a runner's requirements.lock from the server's source tree only when its sha256 equals the hash every result of that runner reports, and otherwise says why the file is absent. The crate root states specimens, timing_caveats and run_completeness (complete, partial, failed, not_recorded for older reports, or not_checked for a report the server did not produce, such as an export from the Browser copy after the server's copy expired).
  • Run configuration. Reports record the agreement thresholds sent, the timeout and its scope, the optimization levels, apply_preprocessing, the API-side preprocessing, the dispatched circuits, started_at and finished_at, and the commit the API image was built from (git_sha; a "-dirty" suffix marks uncommitted changes). The divergence report records analysis_version, the version of the classification and test rules. Runner image digests from the registry are recorded only when the deployment sets QROSETTA_IMAGE_DIGESTS; on a local server the report says "not recorded". Each result carries image_git_sha, the commit its runner or compiler image was built from, and runner_code_sha256 (compiler_code_sha256 for compilers): the sha256 of the bytes of the image's main.py followed by the bytes of every .py file of the installed qrosetta_commons package, in order of relative path. It identifies the adapter that produced the result. To recompute it from a checkout, hash the same concatenation; main.py alone gives a different value.
  • Statevector hashes. A report stored or exported without statevectors (run history, RO-Crates with include_statevectors false, experiment bundles) keeps statevector_sha256 and statevector_length (the number of amplitudes) for every backend. The hash covers the bytes the runner sent: little-endian complex128 amplitudes for every backend. A backend that computes in complex64 (its precision field says so) has its amplitudes widened to complex128 before encoding, so the hash covers the widened values. An older report may carry statevector_len instead; exports and bundles write it as statevector_length. The hash is not stable across replays for every backend: Cirq, for example, can differ in the last bits of some amplitudes between two runs of the same circuit. Compare replayed statevectors by fidelity.
  • RO-Crate export. A run exports as an RO-Crate that conforms to the Process Run Crate profile. It holds the inputs, the dispatched and executed circuits, the per-backend results (counts, or statevector hashes unless statevectors are included), the agreement evidence and the provenance. README.txt at the crate's root, written from ro-crate-metadata.json, describes the crate for a reader without this manual: the report source, completeness, which images ran (specimens), the timing caveats, where each kind of file is, the software version and commit, and a command that checks every file's hash. Every file in ro-crate-metadata.json has its sha256 and contentSize (bytes). The agreement thresholds and, in measured mode, the test's α, target power and total-variation gap are PropertyValues of #agreement-analysis. Links to the source code point at the commit the API was built from, in the repository the server is configured with (QROSETTA_REPOSITORY_URL). They resolve only when that commit has been published there; a commit marked "-dirty" or unknown gets a link to the repository root.

Replaying a run

  1. Take the circuit from the crate's circuit.qasm (circuits/ for a playlist) or from the experiment bundle's inputs/*.qasm, which hold the text as submitted; for a bundle, check each file against the manifest's qasm_sha256. Submit it as literal QASM; a regenerated algorithm can differ from the original.
  2. Send the values the run used, which can differ from those requested: the seed from results.seed (for an experiment, effective_seeds_per_axis); the thresholds from the report's agreement_thresholds, sent explicitly, because defaults can change between versions; an explicit runner list taken from raw_results[].simulator, because an empty list means every runner enabled at the time; and n_shots, apply_preprocessing, optimization_level, runner_config, runner_phases, timing_repeats, timeout_seconds and, when the run used compile-only services, compilers from the report's compilers_requested. The experiment manifest's effective_config records algorithms by name; replay them from the inputs/*.qasm files as literal QASM, as in step 1.
  3. Compare in this order: runner_seed per backend; the dispatched and transpiled circuits, compile_input.qasm and compiled_circuits/; the counts, byte for byte; the statevectors by fidelity (this needs the statevectors, so export with include_statevectors or use GET /jobs/{job_id}/report; hashes alone confirm only a bit-identical replay); then the verdicts.
  4. If git_sha, analysis_version or a backend's runner_code_sha256 differs between the two reports, the verdicts can differ even when the counts are identical, and a changed adapter can change that backend's output. Derive the verdicts again on the new version before comparing labels.

Self-test

The self-test checks an installation against known answers. Each backend's result is compared with an answer computed without any backend, so the test fails even when every backend returns the same wrong state. qrosetta selftest runs it (see Command-line tool); a script can run it through the API in two steps.

  1. Read GET /selftest. Its jobs hold two request bodies for POST /run_batch_suite, a statevector playlist and a measured playlist, with every field set: optimization level 0, preprocessing on, one timed run, 8,200 shots, master seed 20261027 and explicit agreement thresholds. Add target_simulators and change nothing else. The plan does not follow the server's request defaults.
  2. Submit both, wait for each job to finish, and read GET /jobs/{job_id}/selftest-result for each (120 requests a minute). It evaluates the server's own copy of the report (report_source server_job). It answers 404 for an unknown or expired job, and 409 for a job that has not finished, failed before any runner ran, is an experiment, or is not a playlist of the plan.

The statevector playlist has three 3-qubit circuits: x q[0] with two idle qubits; ry(0.3), ry(0.7) and ry(1.1) followed by cx q[0],q[1], cx q[1],q[2] and rz(0.5) q[2], whose eight amplitudes all differ in magnitude; and GHZ-3. The expected states come from a small numpy simulator that builds each gate from its qelib1.inc matrix (services/selftest/reference.py). They are committed in circuits/selftest/expected.json, whose sha256 the plan reports as expected_sha256.

A backend passes a statevector circuit when its result is ok, it declares lsb or msb (equal to the runner registry's value where the registry records one), it returns 2n finite amplitudes with a norm within 10-4 of 1, and its fidelity with the expected state, read in its declared order with both vectors normalised, is at least 1 − 10-5. For the second circuit, a wrong state reaches at most these fidelities: 0.834 under any qubit permutation, 0.559 under bit reversal, 0.874 with either cx reversed, 0.795 with the rz sign flipped and 0.984 with one gate deleted. Rounding the expected state to complex64 changes its fidelity by less than 10-7. GHZ-3 is unchanged by any qubit permutation, so it checks support and amplitudes only.

The measured playlist runs five classical-bit probes, each of which puts every shot on one counts key, and GHZ-3. A probe passes only when the counts are exactly {key: 8200} for the backend's declared order. The probes test the counts-key rules of Bit order per backend through the API's own circuit preparation. GHZ-3 passes with only the all-0 and all-1 keys, 8,200 shots in total, and p(all-0) within 6σ of 0.5 (± 0.0331).

Each result is also checked for the environment it records. A field the runners do not record gives SKIP. The job's circuits and recorded settings must equal the plan's (plan check), and every backend in target_simulators must return a result for every circuit.

What qrosetta selftest adds

Before the jobs, the command reads one fresh probe round of GET /runners and GET /compilers with the local lifecycle token and checks every image under test (--no-images skips this):

  • answers: FAIL when the image is unavailable or did not answer within 5 s; SKIP when a run is using it or an exclusive run holds the server.
  • registry (runners): FAIL when the registry declares a precision other than complex64/complex128 or an order other than lsb/msb; a null value reads "set at run time".
  • commit: FAIL when the image records no commit or one ending in -dirty; WARN when it differs from the API image's commit (a mixed stack); SKIP when the probe row carries no commit.

By default the command tests every runner that answers on a local stack, and the server's default selection on a remote one; --backends KEYS names them. The output gives an Images line with the counts of passed, warned and failed images, a Statevector and a Measured line with each job's status, then one row per FAIL and WARN. Tested and Not tested lines follow: the plan's two sentences, and then each enabled backend left out with its reason, "not started in this stack (profile P)" for a backend whose service the local stack does not run. Each job is saved with its report, summary, crate and selftest-result.json; selftest.json in the results directory holds the combined result. The command exits 9 when any check fails and 0 otherwise, warnings included.

Timing and memory methodology

Recorded conditions

  • Timing caveats. Every result, and the report as a whole, records the conditions that limit how far its timings compare across backends (timing_caveats). The rules are versioned by timing_caveats_version, separately from analysis_version, because they change no agreement label. Each entry has a code, a sentence and the fields it was read from: shared_dispatch (not exclusive, other runs in the same phase), overlapping_runs, server_overlapping_runs, host_load (a host-load notice was open during the run; next item), throttled and compilation_throttled (the CPU quota held the runner for at least 1% of the window), unstable_repeats (timed runs spread by more than 1.3×), mixed_cores, outside_process (container CPU at least 5 ms and 10% above the process's), single_timed_run, no_cpu_quota, virtualised_host, emulated_cpu, emulated_image (the image's architecture differs from the host's), non_x86_64, and across backends cross_backend_core_speeds, cross_backend_cpu_quota and cross_backend_image_commits. The page's "throttled", "outside process", "unstable" and "mixed cores" tags and its "Caveats" list show these records. For a report stored before they were recorded, the page asks the server (POST /timing-caveats).
  • Host load from the qrosetta command. qrosetta start, stop, remove and build (and pull and image probes) open a host-load notice with the API on a local stack, authenticated by the local lifecycle token and kept alive by a heartbeat every 10 s. An open notice holds the run gate like a run, so an exclusive run waits for it. The notice ends with the command, or 30 s after its last heartbeat. Every local result records the notices open while it was in flight (server_overlapping_host_load), and the "host load" tag marks it. A notice begun while an exclusive run holds the gate does not wait; the run records the overlap. A stop or remove notice names its services: a run that then loses its connection to one of them records stopped_by_user: true and an error starting "STOPPED BY USER".
  • Runs that end without a result. When a runner's isolated process ends without a result, the error gives its exit code or signal (process_exit_code, process_exit_signal). The kernel sends SIGKILL both when a container runs out of memory and on a forced stop, so the signal alone does not identify the cause, and the server records none. When the API loses its connection to a runner or compiler, the error lists the possible causes (the container was stopped, the process crashed or ran out of memory, a time limit near the deadline, the network) without choosing one, unless a stop notice covers the service. In Kubernetes mode the error names the cause Kubernetes recorded for the pod (OOMKilled, DeadlineExceeded) when there is one.

Timing windows

  • Warm-up and timed runs. Each backend runs the circuit once and discards the result, then runs it timing_repeats times (default 1). With one timed run every timing is a single sample (timing_samples = 1) and run-to-run variation is not measured. With more, compilation_time_sec and simulation_time_sec are medians (timing_statistic: "median"), recorded with the per-run samples, mean and standard deviation. execution_time_sec is the median compilation time plus the median simulation time; its IQR and standard deviation are those of the per-run totals. The statevector or counts and the memory fields come from the first timed run. In measured mode every timed run uses the same runner seed, so a backend that honours the seed draws the same shots each time. cpu_time_sec and process_peak_rss_mb cover every run and grow with the number of repeats.
  • The two windows. compilation_time_sec is wall clock from t0 to t1: parsing, rebasing, optimisation passes, and building the executable object where the SDK lets the adapter build it separately (the PennyLane tape and device preprocessing, the myQLM and Qibo circuit objects). simulation_time_sec is wall clock from t2 to t3: executing the circuit and returning the statevector or drawing the shots. Building a counts histogram from drawn shots, and converting an SDK's result object into the reported array, fall outside both windows.
  • Conversion outside the simulation call. For Qulacs, QuEST, qsim, Qiskit and cuQuantum the SDK's own entry point (pytket's process_circuits, qsimcirq's simulate and run, Aer's run) converts the circuit inside the call. Their adapters split that call at the native routine: the conversion (tk_to_qulacs, tk_to_quest, translate_cirq_to_qsim, Aer's assemble_circuits and run configuration) is in compilation_time_sec, and the timed run applies the converted circuit with the same routine, options and seeds as the SDK call. The split and unsplit paths gave identical statevector bytes, counts under the same seed and executed texts on 1,080 to 2,200 cases per backend (scripts/adapter_paths/compare_paths.py). On a 4-qubit, 2,200-gate circuit, statevector simulation time fell from 28–37 ms to 1.3–2.3 ms (cuQuantum 50 to 13 ms), with total times within 3%. Each adapter refuses to load with another version of the SDK whose call it reproduces. The disabled Braket and ProjectQ runners still convert inside the call.
  • Sampling from a statevector. In measured mode, a backend with sampling_method: "sv_sample" reads the state from the SDK and draws the shots inside simulation_time_sec, because the shots need the state.
  • Gate fusion. Qiskit Aer (qiskit and cuQuantum) fuses neighbouring gates above its qubit threshold at every optimization level, recorded per run as gate_fusion; qsim fuses into gates on up to two qubits. Both happen inside the simulation and are listed in preprocessing_applied. At levels 1 and 2 the Qibo adapter fuses gates in compilation, except in a circuit that calls a gate its text defines, which runs unfused with a note saying so. Reported gate counts are those of the circuit before fusion.

Backend-specific work inside the simulation window

  • cuQuantum. simulation_time_sec covers Aer's native execution of the assembled circuit: GPU memory allocation, the cuStateVec kernels and the copy of the result to the host. CUDA context initialisation happens in the warm-up run and shows up only in cpu_time_sec.
  • myQLM. myQLM returns a statevector as one Python object per non-zero amplitude (SAMPLE nbshots=0), and building that result is inside the simulation window. Its time and memory grow with the number of non-zero amplitudes: a GHZ state is fast, a dense state slow.
  • quimb. simulation_time_sec includes the search for a contraction path (cotengra's auto-hq optimiser, repeated each run with its caches cleared) as well as the contraction. The search is randomised, so quimb's times vary between timed runs more than a statevector backend's. It runs in the simulating process, with cotengra's worker pool turned off.
  • Qrisp. Qrisp samples the shots and tallies them in one call (QuantumCircuit.run()), so the tally is inside simulation_time_sec. The adapter also wraps Qrisp's multi_measure so that it returns its outcomes in ascending order; without it, a seeded draw maps to different outcomes in different processes. run() samples from the ordered list, so the ordering is inside the window, and the adapter's preprocessing_applied note says so. With h on every qubit and 8,200 shots on one CPU, run() took 14.7 ms with the ordering and 15.0 ms without at 16 qubits, 76 against 66 ms at 20, 223 against 171 ms at 22, and 1.11 against 0.67 s at 24.

Comparing timings

  • What wall clock includes. Timings are wall clock, so they include time the process was not running: waits imposed by the CPU quota (simulation_throttled_sec, compilation_throttled_sec), preemption by other processes (simulation_involuntary_switches_samples), and contention with the other backends of the same comparison, which run at the same time unless runner phases or the Sequential ordering stage them. Each result records concurrent_runs (the runs dispatched in its phase or in a phase in flight beside it, such as the sampled and native groups of a measured run), dispatch_phase, dispatch_wave (its phase's start, end and run count) and overlapping_runs (other runs of the same job that were in their runner process at the same time, from process_started_at and process_finished_at). Concurrent runs share cores, hyperthreads and memory bandwidth: on a 20-qubit measured QFT, concurrent runs took 2.3–3.3× longer than with the Sequential ordering, and the order of backends changed. On a host with hyperthreads, a run whose sibling thread is busy can be 1.5–2× slower with every other check passing.
  • Exclusive runs. The "Exclusive timing run" box (API field exclusive) runs the backends one at a time, and only while no other run is in flight on the server. Each result records exclusive and the wait (exclusive_wait_sec). Without it, every local result records server_overlapping_runs, the runs of other jobs that were in flight (including waiting in a runner's queue) at the same time.
  • Protocol for a performance comparison. Run the comparison as at least three separate exclusive jobs, spaced apart, each with timing_repeats of at least 5. Report the median of the job medians and the range between jobs, treat backends within about 3% of each other as tied, and report quimb with its full range. Check that simulation_throttled_sec is zero and that cpu_max_mhz names the same kind of core for every backend. On the development host this gave medians within 0–3% between jobs for 13 of 14 backends, quimb excepted. Qibo's first timed run at 18 qubits was 14–17% slower in some jobs, which is why one repeat is not enough.
  • Rank marks. The ≈ mark next to a rank (overlaps_next) means this backend's slowest timed run took at least as long as the next backend's fastest in the same job. It reflects the spread within one job only, so ranks without it can still swap between jobs. The "unstable" tag marks a run whose slowest timed run took more than 1.3× its fastest.
  • Different gate counts for the same circuit. Each backend executes the circuit after its own rebase: at 18 qubits one circuit ran as 318, 750 or 1,158 gates depending on the backend. Simulation times compare those workloads; the Gate count column shows each one.
  • Benchmark circuits and structure. The qft preset applies the QFT (q[0] the most significant bit of the input and output index) to |0…0⟩, so every controlled phase has its control in |0⟩ and the output is a uniform product state. Backends that exploit structure (tensor networks such as quimb, Qrisp's factorised state and gate grouping, sparse or decision-diagram methods) run it much faster than its width suggests. For scaling studies, include circuits whose state is entangled and dense, such as random.
  • Threads. Every runner starts with OMP_NUM_THREADS, MKL_NUM_THREADS, OPENBLAS_NUM_THREADS, NUMEXPR_NUM_THREADS and NUMBA_NUM_THREADS set to 1; the values each run saw are in thread_env. RUNNER_MAX_CONCURRENT (default 1) sets how many runs one runner executes at once; further runs queue.
  • CPU time. simulation_cpu_time_sec is process CPU time (all threads) over t2..t3. cpu_time_sec covers the whole isolated runner process: interpreter start, SDK import, warm-up and every timed run.

Memory

  • Fields. Memory is read from the kernel high-water mark (VmHWM). memory_usage_mb (Sim-window RSS delta) is the peak RSS minus the baseline RSS over the simulation window (pre-execute setup plus t2..t3; the high-water mark is reset when the window opens). process_peak_mb (Sim-window peak RSS) is the absolute peak over the same window. process_peak_rss_mb is the peak RSS of the simulating process over its whole life; Resources are ranked by it. Every field ending in _mb is in MiB (220 bytes).
  • Method. memory_method and process_peak_rss_method record how each value was read. Where VmHWM is unavailable they read sampled_10ms (RSS polled every 10 ms, which can miss short peaks) and getrusage (ru_maxrss), and the page shows a badge.
  • Memory the warm-up left behind. The warm-up allocates and frees the memory the timed run needs, and the allocator usually keeps it. The timed run can reuse it without raising the high-water mark, so memory_usage_mb can read near 0 for a statevector of a few MiB (seen for PennyLane at 16 qubits and Qibo at 18). It is the memory the simulation window added. PennyLane-Lightning allocates its statevector when the device is created, during compilation, so its window holds only the copy read out at the end. A fixed allocator threshold that would expose every allocation slowed some backends by more than 3×, so it is not used.
  • Host memory only. Every memory field is host RSS. GPU device memory is not measured, so GPU runs are not ranked by memory: they are listed under unranked with reason gpu_memory_not_measured, and the Performance tab says so.
  • RSS and the container limit. RSS counts the shared libraries a process has mapped, such as the CUDA runtime, so process_peak_rss_mb can exceed the container's memory_limit_mib without the process being out of memory (cuQuantum and quimb read about 545 and 610 MiB under an earlier 512 MiB limit).
  • What dominates memory. For small circuits, process_peak_rss_mb is mostly the Python interpreter and the SDK's import footprint. Compare it with theoretical_statevector_mb, the size of a dense statevector at the backend's precision: 2N × 16 bytes for complex128, 2N × 8 bytes for complex64 (theoretical_statevector_basis says which). quimb holds no dense statevector; its value is computed the same way from the precision it reports. Differences between backends at small N come from their libraries.

Gate counts and rankings

  • Gate count and depth come from the circuit each backend executed: by default the top-level gate statements of its transpiled_qasm (a statement on whole registers, such as h q;, counts once per index), with depth by greedy layering. The PennyLane runners count the operations of the tape the device executes, because their transpiled_qasm decomposes operations such as QubitUnitary into gates that were not executed as such (a QubitUnitary on three or more wires is written as an opaque gate with its matrix in comments). gate_metrics_basis says which.
  • Rankings include only successful runs. Failed runs, and GPU runs in the memory ranking, are listed under unranked with a reason after the ranked rows. The Performance tables have a Device column, and the playlist summary tags the device of the backend in its "Fastest (total time)" and "Lowest process peak RSS" columns.

Resources, queueing and timeouts

  • CPU and memory quota. Each runner is limited to 1 CPU by a cgroup quota, and its math libraries run one thread. Each runner container (local mode) and runner Job (Kubernetes mode) has a 1 GiB memory limit; each result records the limit that applied as memory_limit_mib. A process that uses more than one core (an SDK thread pool the thread variables do not control) is throttled: the kernel stops it until the next 100 ms period, and that wait falls inside the timed window. Every result records the throttled time as simulation_throttled_sec and compilation_throttled_sec, read from the cgroup's cpu.stat just outside each window (null when the file is unreadable). The Performance table tags runs held for at least 1% of the window "throttled". The cuQuantum container has the same quota: its kernels run on the GPU, but its host-side work (circuit conversion, kernel launches, synchronisation, the copy to the host and sampling) is throttled like any other runner's.
  • CPU context. Each result carries cpu_environment: the host CPU model, the quota in cores (cpu_quota_cores, null for none), the process's CPU affinity, the container's memory limit, and cpu_max_mhz for the logical CPUs the process was on at the start and end of each simulation window (simulation_cpus). On a host with cores of different speeds, such as Intel P- and E-cores, the same run takes different times depending on the core the operating system chose; cpu_max_mhz shows which kind it was. An operator can restrict every runner process to chosen CPUs with QROSETTA_CPU_AFFINITY (for example 0-15), recorded as cpu_environment.cpu_affinity_setting. simulation_involuntary_switches_samples counts how often the process was preempted in each simulation window. simulation_cgroup_cpu_time_sec is the CPU time of every process in the runner's container over the simulation window; when it exceeds simulation_cpu_time_sec, part of the work ran outside the simulating process (for example in a worker pool), and the CPU time and memory fields leave that work out. The Performance table tags such runs "outside process".
  • One run at a time per runner. A runner executes one run at a time. When several jobs, yours or other users', target the same runner, later runs wait. The wait is recorded as queue_wait_sec and is not part of any timing. Waits of 0.5 s or more appear in the per-backend details and as a "queued" tag in the Performance tables; shorter values are dispatch overhead. In local mode a run waits at most RUNNER_QUEUE_MAX_WAIT_SEC (default 1,800 s, recorded in the report as queue_max_wait_sec). A run still queued at the cap is not started: it ends with status timeout, timeout_kind: "queue" and never_started: true, and the Summary says it never started.
  • Kubernetes job slots. On a Kubernetes deployment at most k8s_job_slots runner Jobs exist at a time (QROSETTA_K8S_MAX_CONCURRENT_JOBS, set to fit the project's CPU quota). A run waits for a free slot under the same cap, recorded as queue_wait_sec. A run whose pod the cluster's quota did not admit, or that the scheduler did not place, before its timeout also ends with never_started: true. A pod still pulling its image or creating its container at the timeout is a timeout whose message says so (pod_waiting_reason); a pod whose image cannot be pulled is offline. Each result's runner_image names the image by digest (registry/name@sha256:<digest>) when the deployment records digests, and the report's image_digests says, per image, whether the deployment pushed it or kept an earlier build.
  • Timeout scope. The timeout in the Execution chip (the server's allowed range is shown under the field) applies to each backend separately. It covers starting the isolated runner process, importing the SDK, the warm-up run and the timed runs. In local mode it starts when the run leaves the runner's queue, so a wait for a busy runner does not count against it. In Kubernetes mode it starts at Job creation and also covers pod scheduling, image pull and the result upload. The report records the scope that applied. A backend that exceeds the timeout ends with status timeout and timeout_kind: "run"; its process and every process it started (such as a compiler binary) are killed. The page sends the field's value with every run; an API call that omits timeout_seconds gets 60 s, the default the field starts at.
  • Timing samples. With the default of one timed run, a difference between two backends smaller than either one's run-to-run variation cannot be read from one report. Set Timing repeats above 1 for a median and a standard deviation per backend, or use multi-run mode to compare separate runs.

Compile-only services

A compile-only service turns the run's circuit into another circuit and records the text. Its output is never simulated, has no timings, and is not part of the agreement comparison: compiled circuits are kept in the report's compiled_circuits, apart from raw_results. Tick levels in the Compile-only services chip's popover, or send compilers (compiler id → list of distinct levels) with /compare, /compare_measured, /run_batch_suite or POST /experiments. A request holds at most one compile per level of every enabled compiler for each circuit: 17 with the eight compilers. GET /compilers lists them with the versions each running image reports (versions: pip SDK versions, components built from source, build-file sha256 and image commit; null in Kubernetes mode, where no compiler runs between jobs), and the popover shows them under each compiler.

How compiles run

  • Input. Every compiler receives the same circuit, recorded as compile_input: the submitted circuit as the API prepares it for statevector runners (terminal measurements removed, then the run's API preprocessing). Compiled circuits therefore carry no measurements, also in measured mode. In statevector mode the compile input is the dispatched statevector circuit. A measured-mode circuit with mid-circuit measurement, reset or classical control is not compiled; each requested compile is recorded with dispatch_status skipped and the reason.
  • Order and sharing. Compilers run after the run's simulators have finished, through the same queue and timeout as runners, so a compile never overlaps a timed run of its own job. They always run as a shared dispatch: an exclusive run of another client waits for them, and other jobs count a running compile in server_overlapping_runs. Each compiler service runs two compiles at a time, each single-threaded; BQSKit runs one, because its runtime binds fixed ports. A further compile waits in that service's queue, so a busy service can delay another client's compile. The live status grid lists each compile while it runs.
  • Completion. The report is complete only when every compile has finished or timed out, so a slow compile (BQSKit level 3 beyond a few qubits) delays it. A compile that fails or times out is recorded with its status and reason and does not affect the simulator results. In a compile-only run (simulate: false), a circuit whose every compile failed, was refused or was skipped is reported like a run whose every runner failed: the job is failed with "all N compiles failed" (in a playlist, when this holds for every circuit) and keeps its report.
  • Refusals. An adapter refuses an input it cannot compile correctly, and rejects an output that fails its check. Such a compile has refusal (the reason) and refusal_kind (input or output_check), also as columns of tables/compiled_circuits.csv in a crate. The CSV's reason column gives the reason for every compile without output: the refusal, else the recorded error (the skip reason, "TIMEOUT (N s)", or the compiler's error text, which the crate's provenance.json also holds). The Summary lists every compile with its gate counts or reason, those without output first; a share link shows refusal reasons and no other error text.

Records

The report records the request as compilers_requested. Each record's key is <compiler>~opt<level>~run1 and holds the output text (transpiled_qasm), the passes that produced it (passes_applied), gate metrics counted from that text, the pip SDK versions (sdk_versions), the programs the image built from source (native_components: staq, Quartz and Synthetiq, with the source archive's URL and sha256, compiler flags or patches, and Quartz's ECC set hash), the sha256 of the image's build files (build_files), the image's runtime_environment and image_git_sha, and compiler_code_sha256. The Circuits tab shows the compiler input and each output. Crates hold them as compile_input.qasm and compiled_circuits/<key>.qasm (in a playlist, compile_inputs/<task>.qasm and compiled_circuits/<task>/<key>.qasm); each compile is a CreateAction from the compile input to its output, and each native component a SoftwareApplication. For a compiler that produced output, its build files are included under compilers/<name>/ when the server's copy has the sha256 the image reported: the Dockerfile and requirements.lock, and for Quartz also shift10-normalise.patch, gen_nam_ecc.cpp, quartz_greedy.cpp and Nam_complete_ECC_set.json. A file whose hash differs (the image was built from another commit) is left out.

Outputs are deterministic on a given image: the same circuit, level and image give the same text in every job. BQSKit's numerical resynthesis does not carry over exactly to another image: on another Python or BLAS build its angles can differ in the last digits while gate and two-qubit counts match. Cite the record's text rather than a regenerated one.

Gate counts

gate_count is the number of top-level gate statements in the output text (a statement on whole registers once per index), and circuit_depth its greedy layering, one statement per layer slot whatever the gate. Barriers are neither counted nor treated as aligning the wires, so the depth can be lower than Qiskit's depth() of the same text. Each record also has multi_qubit_gate_count (statements on two or more qubits) and gate_counts (statements per gate name). The compilers write different gate sets: staq keeps ccx, cu1 and swap as single statements, Quartz writes h, x, rz and cx, Cirq cz and single-qubit gates. A smaller gate_count therefore does not mean a smaller circuit across compilers; to compare compilers, translate the outputs to one gate set and count there.

The compilers

Up to 10 qubits, every output is checked against the compile input with Qiskit when it is produced, and a compile that fails the check is recorded as a refusal, never as output. Above 10 qubits the passes say the output is not checked. Synthetiq takes at most 3 qubits, so all its outputs are checked.

Summary

The headline says how many backends returned a result, names failed ones as Offline, Error or Timeout, and names the backends that differ from the others. It is built from the pairs that differ; an inconclusive pair counts as neither agreement nor difference. A statevector pair differs when it disagrees (Agreement classification); a measured pair differs when it is distinguishable beyond shot noise or a single-bit marginal differs. The headline takes the first of these forms that fits:

  • Named backends. One set of at most four backends, fewer than half of those with a result, is the only set of that size present in every differing pair. Those backends are named with how many they differ from ("Qibo differs from all 13 other backends"; "Qrisp differs from 7 of 13 other backends"), backends in the set that agree with each other together ("PL Default and PL Lightning agree with each other and differ from every other backend (12)"), followed by a sentence about the rest, among which no pair differs.
  • Groups. The backends that differ from at least one other split into two to four groups, at least two of them with two or more members, with no differing pair inside a group and every compared pair between groups differing. The groups are listed as differing from each other; a backend that differs from none is named apart.
  • Pairs. Up to four differing pairs are listed by name. In measured mode, when each backend of these pairs differs from no other, the headline suggests rerunning with another seed, since a single flagged pair can be a chance result.
  • Spread. The backends that differ from more than half of those they were compared with are named, those that agree with each other together and the groups with the largest difference first, up to four, and the rest in a sentence of their own ("Qrisp and TorchQuantum also differ from more than half of the backends they were compared with"); then the differing pairs among the others.

Each named backend or group carries the size of its difference, measured against the backends the headline does not name, so a pair of two named backends does not set it: the lowest label-aligned fidelity (statevector), or the median and range of the total variation (measured). When groups differ, the size is taken over the pairs between groups. In measured mode, a named backend that differs from fewer than half of the others and is consistent with all the rest gets a caveat: with many pairs tested, one backend's unusual sample can differ from a few others by chance. In simulation with every backend correct at 8,200 shots, the full-distribution test flagged a pair in 0.6–1.1% of 14-backend runs, and with the single-bit marginal tests 3.9–4.8% of runs showed a flag. A multi-run report counts runs in the same sentences ("all 4 PL Default runs").

A measured pair that is distinguishable under Benjamini–Yekutieli but not under Holm's family-wise correction, with no differing single-bit marginal, is listed on its own line as significant under BY only and does not shape the headline. When one backend is in every such pair (two or more), the headline names it. "No single-bit marginal differs" appears only when the marginal test ran, which needs keys of two or more bits. In measured mode the full-distribution and marginal counts are given separately, with the number of inconclusive pairs and the shots the power model asks for ("at least" when the recommendation is a lower bound, recommendation_is_lower_bound). When backends timed out, the next step suggests raising the timeout unless the run already used the server maximum. A pair that differs shows that one of the two is wrong; the report does not decide which.

The Backends table gives per backend its status; how many backends it differs from (hover for the names and the size of the difference; red for the backends the headline names, gray for the others; pairs significant under BY only added as "+N BY only"); in measured mode how many it is inconclusive with; its declared bit order, precision, total time and peak memory. Red in the table marks exactly the backends the headline names.

Evidence follows, with a legend for the mode. Statevector pairs are grouped in the three label groups. Measured pairs are grouped by measured_assessment only, each pair once with its JS/Hellinger distance label as detail; pairs whose single-bit marginals differ have their own block; inconclusive pairs are split by cause; not comparable pairs carry the reason. Lists of differing pairs are never folded and are ordered by the backend they share; lists of agreeing pairs over twelve items are folded. Power is shown to three decimals with the α/(m·c_m), m and c_m it was computed at. A collapsible section lists the analysis version and git commit, then per-backend run details.

A compile-only run (simulated: false) shows a headline naming the compiles that were refused, rejected by their output check, not run, timed out or failed, then its compile records. A compile-only playlist shows one row per circuit with the compiles that returned a circuit and those that did not.

Performance

A run on a GPU carries a GPU tag under its name (hover for the GPU), and the header says so when any run was on a GPU. Each column uses one number format: fixed decimals chosen so its smallest value shows three significant digits, or scientific notation throughout when a value is below 1e-6. After "Caveats", the header names conditions in this run that can bias a comparison (backends ran at the same time, other jobs on the server, throttling, unstable repetitions, CPUs of different speeds, one timed run per backend); "Measurement notes" gives the details. With Timing repeats above 1, each time cell shows the median with ± the sample standard deviation below it; the header gives the number of timed runs when every backend had the same, and each cell gives n when they differ. Process Peak RSS includes interpreter start, SDK imports and the warm-up run, so for small circuits it is mostly the SDK footprint. Each column's tooltip gives its measurement window.

Agreement

The heatmap colours each pair by the same verdict as the Summary, with a symbol per class that the key below repeats: = agree or consistent within shot noise, φ agree up to a global phase, ↺ agree after the declared bit reversal, P agree only after a qubit permutation, N agree after normalisation, ≠ disagree or distinguishable, ? inconclusive, – not comparable. Click a cell to open its evidence: label, metrics, tolerances, statistical test and provenance (seeds, ordering, SDK versions, preprocessing). Labels are shown in words with the recorded code in the tooltip; the pair list can be filtered by verdict and by backend.

Each statevector row shows the fidelity under the transform its label names. For a pair that disagrees it is the fidelity in the basis the declared orderings imply (F(bit-rev) for an lsb×msb pair), with the other basis' value added when the pair matches only there. A pair that agrees up to a global phase shows that phase. Agreement after the declared bit reversal is blue on badges, legends, heatmap and export charts. A measured row leads with its shot-noise assessment; its JS/Hellinger distance label follows in gray after "distance:" and does not decide agreement.

Divergence matrices (collapsed) hold the N×N fidelity, global phase offset arg⟨a|b⟩, JS divergence (nats) and Hellinger values. Each number is the direct value, before any bit reversal; for a pair compared after the bit reversal its declared orderings imply, the value in that basis is shown below it with ↺. Cells are coloured by the pair's verdict, not by the number, so an lsb×msb pair that agrees after the declared reversal is coloured as agreeing although its direct fidelity is low. OFF, ERR and T/O mark failed runs, n/c a pair that is not comparable. Cells show four decimals, more for a fidelity that would otherwise round to 1, and three significant digits in scientific notation below 1e-3; hover for the unrounded value.

The table has one row per distinct circuit text: rows that list several backends hold byte-identical texts with the same recorded gate count and depth. Untruncated reports are kept on the API's local disk within the storage budget, and the server keeps at least 1,024 MiB of that disk free (limits.job_storage_min_free_mib, QROSETTA_JOB_SPILL_MIN_FREE_MIB). One 18-qubit statevector circuit run on 14 backends takes about 78 MB. While either limit is crossed, a new run is refused with HTTP 503 and a Retry-After header, and the message names the limit. A playlist or experiment checks before it writes each circuit's result; when the storage is full it stops, and the job fails with a message naming the circuit and the limit. A single-circuit run always keeps its report, so runs already in progress can take the storage past its budget. Before a run is refused, and before a running playlist or experiment stops, the server deletes finished jobs older than 30 minutes, oldest first, until the storage is back within both limits.

Report source in a crate

Every crate's provenance.json records report_source, set by the export route and never read from the report: server_job for the server's copy of a job, upload or not_recorded for a saved run by how it was saved, and client_supplied for POST /export, whose contents (git commit, versions, circuit texts) are as the requester sent them. The same value is report_source in results.json and the #report-source PropertyValue of the crate and of its agreement analysis. For any source other than server_job, ro-crate-metadata.json asserts no completed or failed status for the backend runs and compiles, gives SDK versions and the platform version only as supplied text, and the crate carries no runner or compiler lock files and no links to a commit. A run uploaded to history keeps the uploaded job_id as source_job_id.

Using the API from a script

/openapi.json describes every route, its request fields, the status codes it can return and the shape of the reports; /docs and /redoc show it. A run is a POST that returns a job envelope {job_id, status, ...}; poll GET /jobs/{job_id} until status is completed or failed. Its results has one of three shapes:

  • a single-circuit report (/compare, /compare_measured): raw_results is a list with one entry per run, keyed by simulator; divergence_report.pairwise_agreement holds one record per pair; n_shots is present only in measured mode;
  • a playlist report (/run_batch_suite): mode and benchmark_summary, one single-circuit report per task in task order, each with task_name (the name followed by "(nq)"), task_qubits and task_request (the task as sent, including its name); a task that failed before dispatch is {task_name, task_qubits, task_request, error};
  • an experiment: {experiment_summary} only; the per-circuit data is in the bundle.

GET /config starts with server, which a script reads first: platform_version, api_levels ([min, max], the API levels this server serves; a change that removes or renames a route or field raises the maximum, and the previous level stays served), analysis_version (the comparison code that labels new reports), git_sha (the commit of the API image) and features, a map from feature name to version that only grows. status_labels gives the word and tooltip ({label, hint}) the page shows for each live status: runs for the values of runner_statuses, tasks for a playlist circuit, and phases for the job's phase.

GET /config also publishes request_defaults, the value the server uses for every request field a run omits, read from the request schemas. The page starts its controls from these values, so a script that omits a field gets what an unchanged page sends. request_defaults.requests has one entry per run endpoint (compare, compare_measured, run_batch_suite, experiments), each with fields and, for playlists and experiments, items (the fields of one task or circuit). A field with server_fills: false must be sent; any other field has a default, and where that default stands for a decision the server makes, when_omitted says which: an omitted seed means the server generates a master seed and records it, an empty target_simulators means every enabled backend that is available, and an omitted thresholds means the values in request_defaults.agreement_thresholds. The defaults are the same for every endpoint except mode, which a playlist must send and an experiment takes as measured when omitted. request_defaults.compile_only says what makes /compare or /run_batch_suite compile-only: simulate: false, at least one entry in compilers, and empty runner_config, runner_phases and target_simulators.

POST /plan turns a workspace into the run requests the Run button would send, without running anything; the page plans every press of Run through it. Its body has source (single or playlist), circuits (playlist items: algorithm, qubits, name, qasm_string, source; one {qasm_string, name} for a single circuit), modes, preprocessing (on, off or both), compilers, name and settings, each request field given as {value, source} with source flag, set or replay. A field left out of settings stays out of the planned requests, so the run route applies its default. The answer lists runs (endpoint, kind, mode, title, the payload to send unchanged, and each payload field's sources) and problems, each with a code, params, a message and, where they apply, run_index, circuit_index and line. The codes are playlist_empty, editor_empty, no_mode, compile_only_needs_one_setting, playlist_too_long, bundled_over_prep_limit, experiment_too_many_cells, circuit_too_large, request_too_large, invalid_request, bypass_needs_account, and, with check_circuits: true, circuit_refused for every literal circuit the run route's checks refuse. The body may be up to 4 MiB (limits.max_plan_request_bytes), so the plan can report a request over the 1 MiB run limit, at 120 requests a minute per client (limits.plan_rate_limit).

In measured mode the verdict of a pair is measured_assessment (distinguishable is the disagreement), together with marginal_assessment. The pair's agreement field compares the JS and Hellinger distances with their thresholds and ignores shot noise, so a check that reads only agreement can pass a distinguishable pair or fail a consistent one. In statevector mode agreement is the verdict.

Each pair also records pair_verdict, the verdict every view of the page shows. Its verdict is not_comparable, differs_by_only (measured: significant under Benjamini–Yekutieli only, not under Holm, and no single-bit marginal differs), differs, inconclusive, agrees, bit_order (agrees after the bit reversal the declared orderings imply) or unassessed, beside the flags differs (the badge), differs_by_only, agrees and inconclusive. divergence_report.backend_verdicts holds the per-backend counts of the Backends table and headline_model, the backends the Summary headline names. Reports from analysis versions before divergence-2026.10.27.1 lack these fields; the three summary routes above compute them for any report with this server's rule, and the page uses them for such reports.

Live statuses in runner_statuses use the same keys as the results: a backend at one level is its id, several runs are <id>~opt<L>~run<N>, and a compile is always <id>~opt<L>~run1, as in compiled_circuits. progress (playlists and experiments) stays on the job after it finishes. phase is queued (accepted, not started), dispatching (preparing circuits, waiting for the run gate, runs and compiles), analysing (the pairwise comparison and the report; the running view shows ANALYSING), exporting (writing the results to the server's job store) or done; a playlist moves between dispatching and analysing once per circuit.

Errors have the body {"detail": ...}. A 422 means the request does not match its schema (a wrong type, a value out of range such as a level above 3, an unknown field), with a list of {loc, msg, type} as detail. A 400 means the request is well formed but this server cannot run it: a circuit that does not parse, an unknown or undeployed backend or compiler, a level a compiler does not offer, a circuit or playlist task over the qubit limit (a playlist error names the task as tasks[i], counted from 0). A 413 is a body over the request limit; one over the proxy's 5 MB limit gets the same JSON shape. A 409 is a job in the wrong state or of the wrong kind (for example an ordinary job asked for an experiment bundle). A 415 is a body sent to a JSON route without a JSON Content-Type (application/json or a +json type). A 403 with the detail "Requests from other sites are refused." is a POST, PUT, PATCH or DELETE whose Origin header names another site; a script that sends no Origin header is not affected.

Run, export, render, lookup and account routes are rate-limited. A request with a bearer token this server signed that has not expired counts against its account; any other request, including one with an expired or foreign token, counts against its client address; requests with the local lifecycle token share one count. Each route has its own count, whatever the job or run id in its path.

Command-line tool

qrosetta starts and stops a local stack and runs, follows and saves jobs on any server. It needs Python 3.11 or later and uses the standard library only. Install it from PyPI (pipx install qrosetta) or run ./qrosetta from a checkout; the host requirements and setup steps per distribution are in the README. qrosetta help all lists every command and qrosetta help command (or --help) gives its flags and examples. Commands marked experimental print a notice and may change their behaviour and JSON (schema @0).

Global options, accepted anywhere on the line: --json, --server URL|NAME (a URL, or a [servers.NAME] table of the config; default local), --config FILE and --project-dir DIR (the checkout whose compose file to use). In installed mode, pull fetches the release's images by digest and build builds them from the build kit the package carries; in a checkout, build builds them from the working tree. The release does not publish the myQLM, cuQuantum and BQSKit images; qrosetta build NAME builds them.

The published port

An address chosen with --bind, QROSETTA_HTTP_BIND (in the environment or the checkout's .env) or [lifecycle] bind is used as given, and start refuses it when another program holds it. When no address was chosen, start uses the address it recorded for the project, else 127.0.0.1:8080. When another program holds that port, it takes the first free port of 127.0.0.1:8081 to 8089, says which (for example "Port 8080 is in use by another program; using 8081."), and records the address in the project's stack settings; config show lists it as chosen by start. status, run and the other commands find the local server there. stop keeps the address; remove forgets it. start never stops a program that holds a port.

JSON output

With --json every command writes one JSON object to stdout, also on failure: {schema, cli_version, server, ok, exit_code, outcome, data, warnings, error}. schema names the payload type as qrosetta.cli/name@n (for example qrosetta.cli/run-result@1, status@1, selftest@1), so renaming a command does not rename its schema. error is {code, reason, message, hint, http_status, detail}, with the exit code's name as code, a snake_case reason and the server's detail verbatim; outcomes (exit 3 to 9) leave error null and data complete. Within a schema version fields are only added, so a consumer should ignore fields it does not know. Server objects embedded in data (from /config, /runners, the summary) carry their own versions; the report itself is never embedded, and files are referenced by absolute path. The JSON Schemas ship with the package in qrosetta_cli/schemas/. Without --json, data goes to stdout and progress, warnings and errors to stderr; on a UTF-8 terminal check rows carry marks (✓ ✗ !), otherwise the words PASS, FAIL and WARN, and colour follows [output] color, NO_COLOR and CLICOLOR_FORCE.

Accounts, history & autosave

An account is optional. Signing in, or registering with an email and password through the Login / Register button, turns on automatic run history for single runs and playlists started from the page: each is saved to your account when it completes, under its run name. Experiments are never saved; their result is the bundle you download. Runs started through the API are not saved automatically; save one with POST /history/runs/from_job/{job_id} (see Reports and exports) while the server still holds it. Without an account, results exist only in your browser for that session.

Your Run History lists past runs. Rename them, download their stored reports, or delete them singly or in bulk. Stored reports have their statevectors removed; statevector_sha256 and statevector_length are kept. While a run is in progress, past runs can be renamed, downloaded and deleted but not opened, because opening one would replace the view of the run. A saved run opened from History has the same heading as when it ran, with its mode and shot count. A run uploaded with POST /history/runs, instead of saved from this server's job, is tagged Uploaded in the Viewing Past Run banner, and one saved before the server recorded the source is tagged Source not recorded; the History list itself does not show the source.

The Save and share box in the Circuits tab saves the run on screen to your history (also a run started before you signed in, while the server still holds it) and creates read-only links. Create link gives a /share.html#<token> address that expires after 1, 7, 30 or 90 days. An optional label names the link in your own list and is never shown to its recipients. A link created from a playlist circuit's view opens on that circuit. Anyone with the address sees the run's name and save time and its circuit texts: the submitted circuit, the dispatched circuits and each backend's executed circuit with its transforms, SDK versions, gate count and depth, plus the compiler input and compiled circuits when the run had any. An uploaded report is marked as uploaded. The page shows no results, timings, error messages or account details. The token is shown once and the server stores only its SHA-256; it sits after #, so browsers do not send it in requests or referrers. Revoke a link in the same tab. Deleting the run or the account deletes its links, and a deactivated account's links stop working.

Sessions and the account menu

A session lasts 30 minutes, measured on the server's clock from the sign-in token's issue time, so a computer clock that is fast or slow does not end it early. When it expires, the page signs you out and says that runs started from then on are not saved; pressing Run with an expired session asks first. If it expires before a run finishes, the page offers Sign in and save, which saves the run after you sign in again, while the server still holds the job. When one press of Run starts a statevector and a measured run with a Run Name, History saves them as "name (Statevector)" and "name (Measured)".

Logout, Change Password and Delete Account are in the menu under your email address in the header. Logout ends every session of the account, in this browser, other browsers and qrosetta, because the server refuses every token issued before it; it also clears this browser's list of the account's recent jobs (an expired session keeps the list, so a pending job can be resumed after signing in again). Change Password asks for the current and the new password (POST /auth/password) and ends every other session; this browser stays signed in. Delete Account asks for the password (DELETE /auth/me takes it in the body, at the sign-in rate limit), then removes the account with its saved runs and circuits; a token issued before the deletion stops working. The sign-in token is kept in this browser's local storage. The page's Content-Security-Policy runs only scripts from this server, and other sites cannot frame the page.

Run names

Run names may contain any emoji (with skin tones, variation selectors and joiners, such as 👩‍🔬) and the zero-width joiner and non-joiner that Persian and Indic scripts use. They may not contain control characters, line or paragraph separators, direction marks, overrides or isolates (U+200E, U+200F, U+061C, U+202A–U+202E, U+2066–U+2069), or the invisible characters soft hyphen, zero-width space, word joiner, invisible operators (U+2060–U+2064), byte-order mark, Hangul fillers and interlinear annotation marks. The message names the character and its position. The browser and the server check the same fixed list, so a name the page accepts is accepted when the run is saved. A saved run or circuit name needs at least one visible character: spaces, joiners, variation selectors, combining marks on their own (such as U+0301), format characters, the braille blank U+2800 and the object replacement character U+FFFC do not count. A name saved before these checks is shown and exported with the refused characters removed.

Autosave to a folder

Independent of an account, the Execution chip offers Auto-save results to a folder: each completed run is written as a JSON file to a folder on your computer, with nothing uploaded. This needs the File System Access API, which Chromium-based browsers such as Chrome and Edge provide; other browsers show the option disabled with a note.

Limitations

  • Agreement between backends is not correctness. Backends that agree can all be wrong, and a backend that differs from the others can be right. QRosetta compares backends with each other; only the self-test checks them against independent answers, for a few small circuits.
  • Measured-mode thresholds are descriptive. The JS and Hellinger cut-offs are configurable and depend on the shot count; measured_assessment, from the statistical test, decides whether a pair disagrees.
  • Permutation search is bounded. Exhaustive qubit-permutation matching stops at 7 qubits. Larger cases report too_many_qubits.
  • Default timings are not a benchmark. By default each backend has one timed run and all backends run at the same time, competing for the host. For a comparison, follow the protocol in Timing and memory methodology. Results hold for one host, a 1-CPU quota and one thread.
  • Pairwise flags can concentrate on one backend. Every pair that shares a backend reuses its sample, so one unusual sample can make several of that backend's pairs distinguishable at once. When all the flags of a run involve one backend at modest p-values, rerun with another seed or more shots before drawing a conclusion.
  • A residual disagreement needs investigation. None of the registered transforms explained the difference. The cause can be an unregistered convention, an environment limit, or a defect in a backend or its adapter.

Adding a simulator

Every runner implements the same contract: process_run (statevector) and process_run_measured (counts), built on the shared measurement code that does the timing, memory measurement, qubit-limit check and result assembly, so every backend is measured the same way. The step-by-step guide, including how to determine a backend's qubit ordering and how to register it, is CONTRIBUTING.md in the repository.

FAQ

Why would two correct simulators disagree?

Usually because of a convention: a different declared qubit ordering or an unobservable global phase. The agreement classification accounts for these, so a convention difference is reported as agreement. A difference that no declared convention explains is reported as a disagreement.

Is a "distance exceeds threshold" pair a bug?

Not by itself. The distances stayed above the descriptive thresholds after every registered transform. Check the pair's measured_assessment: if it is consistent_within_shot_noise, sampling alone produces such a difference at this shot count; if it is inconclusive_low_shots, rerun with more shots when resolvable_by_more_shots is true. Only distinguishable indicates a real difference, whose cause can be an unregistered convention, a resource limit, or a defect in a backend or its adapter.

Does QRosetta modify a backend's output?

No. Each adapter shapes the backend's raw output into the reported form (a counts histogram keyed by classical bits, a statevector array), and the report stores that. Bit reversal, phase alignment and permutation matching are analysis steps reported with their numerical effect. The input circuit can be changed before dispatch; every such change is listed in preprocessing_applied (see Circuit preprocessing).
